### Добавлено — режим `ARTIFACT_DRY_RUN` и выключение SAST (прямые решения пользователя)

- `ARTIFACT_DRY_RUN=true` (`app/core/config.py`, `app/pipeline/steps.py::PublishStep`): весь
  конвейер выполняется по-настоящему, но шаг публикации не пишет байты в целевой Artifactory —
  только проверяет достижимость/авторизацию (HEAD) и завершает конвейер с пометкой
  `dry_run=true`, не переводя заявку в `approved`. Нужно для проверки реальными кредами от
  продового Artifactory без риска записи в него. Задокументировано в `docs/testing.md`.
- `SAST_ENABLED=false` — SAST (и локальный semgrep, и идея триггера внешнего SAST-пайплайна)
  временно выключены целиком, "на первых порах" — код уже поддерживал чистое выключение
  (`_ContentScanStep.run` отдаёт `pass` без блокировки), правок не потребовалось, только
  решение и документация (`docs/ci-parity-gaps.md`).


### Скорректировано — все пакетные менеджеры обязательны

По прямому замечанию пользователя пересмотрена формулировка в `docs/ci-parity-gaps.md`,

### Исправлено — неверное предположение про Artifactory/Nexus

По прямому замечанию пользователя пересверил, как `pt-package-review` (реальная CI-версия)
работает с артефактори — оказалось, production использует **исключительно JFrog Artifactory**
(AQL-поиск, copy API), Nexus нигде не используется. Моя локальная проверка backend'а ранее
использовала `ARTIFACT_STORE=nexus` (дефолт в `.env.example`) — валидный тест кода, но не
показательный для реальной инфраструктуры. Дополнительно нашлось более существенное
расхождение: CI-версия публикует пакет server-side copy'ем внутри Artifactory (пакет никогда
не проходит через процесс как байты), прототип — скачивает с публичного upstream и делает `PUT`
сырых байт. Неизвестно, разрешает ли реальный production Artifactory прямой `PUT` в
moderated-репозитории — открытый риск, тот же класс проблемы, что и найденный ранее EULA-гейт
Nexus. Подробный разбор — `docs/ci-parity-gaps.md`, новый раздел. Поправлены
`docs/configuration-model.md`, `docs/migration-to-go.md` (фаза 5 — приоритет `generic`, не
`nexus`), добавлена явная пометка в `docs/integrations.md`.


### Проверено локально — полный стек, реальный золотой путь

Поднят полный докеризованный стек (изолированно, `-p modrepo-verify`, снесён после проверки:
все контейнеры/тома/сети удалены, временный `.env` не закоммичен) — `db`/`redis`/`minio`/
`nexus`/`api`/`worker`/`beat`/`web`/`nginx`.

- **Правка `AddPackages.tsx` (поиск сначала) — типобезопасна**: `tsc -b && vite build` прошёл
  без единой ошибки; собранный бандл, отданный через nginx, содержит новые строки интерфейса
  («Найти пакет», «Не найдено в базе», кнопка перехода в добавление).
- **Полный золотой путь пакета `six==1.16.0` (pypi) — все 9 шагов конвейера реально
  выполнены** (не заглушки): db_check → blacklist (4 правила) → quarantine (реальная дата
  публикации 2021, математика 14 дней) → license (реальная проверка MIT по справочнику) →
  download (реальное скачивание с pypi.org, sha256 сошёлся) → vuln_scan (реальный запрос к
  osv.dev, `OSV_SOURCE=api`) → banner_scan (реальный YARA по 6 файлам) → sast_scan (реальный
  semgrep, 6 правил) → publish (реальная выгрузка в Nexus). Результат: `approved`, рабочая
  `pip install -i .../pypi-internal/simple six==1.16.0`. Артефакт подтверждён в Nexus (HTTP 200
  на HEAD), временный объект в MinIO подтверждённо удалён после публикации.
- **Найдена и обойдена реальная проблема окружения, не связанная с кодом сервиса**: свежий
  `sonatype/nexus3:latest` (3.96.0) требует принятия EULA через
  `POST /service/rest/v1/system/eula` до разрешения любых операций с содержимым репозиториев —
  без этого шага все запросы к содержимому (включая HEAD от самого сервиса) получают 403, не
  404. `make bootstrap` этого не делает. Стоит либо запинить `NEXUS_IMAGE` на версию до
  введения этого гейта, либо добавить принятие EULA в bootstrap-скрипт — иначе первый
  разработчик, поднявший стек с нуля на актуальном образе, упрётся в то же самое.
- Заодно поймана и исправлена собственная ошибка в процессе: `POSTGRES_PORT` в `.env` — одна
  переменная, используемая и для публикации порта на хост, и для внутреннего подключения
  приложения к БД; переопределение только ради обхода конфликта порта с параллельно работающим
  `sentrix` на хосте ломало внутреннее подключение. Верно — не трогать `POSTGRES_PORT`
  (внутренний порт БД всегда 5432 независимо от публикации), а публикацию на хост для db
  отключать через compose-оверлей (`ports: !reset []`), если host-доступ не нужен.


### Добавлено — backend-go, pipeline runner (шаги 0–3)

- `backend-go/internal/pipeline` — конвейер как исполняемая логика (не только хранение
  результата): `db_check`/`blacklist`/`quarantine`/`license`, оркестратор `Run()` с сохранением
  в `pipeline_step` и точечным обновлением `request_item`/`package_version`.
  `BlacklistPolicy`/`LicensePolicy` — интерфейсы с in-memory реализацией на первое время.
- 5 интеграционных тестов на реальном Postgres (все PASS), включая ключевой сценарий —
  подтверждение, что шаг `license` не останавливает конвейер при `warn` (в отличие от
  остальных), с проверкой и `pipeline_step`, и `request_item.status`/`current_step`.
- Шаги 4–8 и обработчики решений с sibling-propagation — сознательно не реализованы в этом
  шаге, зафиксированы как следующий (самый рискованный по потере поведения).

  16 доменных структур (порт `app/db/models.py`), репозиторий поверх pgx для основной
  агрегации (package → package_version → moderation_request → request_item → pipeline_step),
  интеграционные тесты на реальном Postgres (happy path на 9 шагов, идемпотентность заявок).
  Pipeline runner как исполняемая логика — ещё не перенесён, см. `docs/migration-to-go.md`.
- `docs/ci-parity-gaps.md` — явный трекинг разрывов с функциональностью CI-версии
  (pt-package-review/moderated: 6 недостающих пакетных менеджеров, SBOM, sandbox-сканирование,
  YouTrack-эскалация и т.д.), чтобы ничего не потерялось при переносе на Go. Дополнено разделом
  "Оповещения и упрувы" по прямому запросу: подтверждён реальный разрыв — `decide_security`/
  `decide_license` не проверяют `prevent_approval_by_author` (можно одобрить свою же заявку,
  если роли назначены так, что это в принципе возможно); подтверждено, что `rescan_approved()`
  корректно перепроверяет уже одобренные пакеты после обновления OSV-снапшота и не блокируется
  `security_override_at` — это оказалось строже CI-версии, не разрывом.

## [0.1.0] — прототип

- Self-service портал модерации внешних пакетов (`pypi`/`npm`/`go`/`nuget`): заявки, конвейер
  проверок (blacklist/карантин/лицензия/уязвимости/баннеры/SAST/публикация), параллельные
  согласования юриста и DevSecOps, admin API, React/TS SPA. Реализация — FastAPI + Celery +
  Postgres + Redis + MinIO, см. `docs/architecture.md`.
