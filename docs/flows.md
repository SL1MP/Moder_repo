# Флоу сервиса и каждой роли

Описание относится к действующему Go API и React-интерфейсу.

## Общий флоу (сквозной сценарий)

1. Пользователь выбирает менеджер и отправляет список, файл зависимостей или
   ссылку GitLab; проверку наличия можно выполнить без создания заявки.
2. API валидирует формат, выделяет прямые зависимости и при поддержке
   менеджера может заранее раскрыть транзитивное дерево.
3. Для уже опубликованной версии API сразу возвращает публичную ссылку и
   команду установки. Для новой версии создаётся отдельный `request_item`.
4. Worker забирает элементы из очереди PostgreSQL и выполняет шаги
   `db_check → blacklist → quarantine → license → download → dragon_scan →
   vuln_scan → sandbox_scan → sbom → publish`.
5. Результат каждого шага сохраняется немедленно, поэтому UI показывает
   реально выполняемый шаг. Лицензионное и security-согласования могут
   ожидаться одновременно.
6. OSV применяется только к PyPI и npm и носит advisory-характер. Sandbox
   обязателен там, где применим, и не выполняется для Docker.
7. После всех обязательных проверок и решений пакет публикуется в hosted-
   репозиторий Nexus своего формата. Успешная публикация синхронизирует статус
   всех прежних заявок на ту же версию.
8. Пользователь получает публичный URL, хеш и команду настройки штатного
   клиента пакетного менеджера.

## Роль: Разработчик

1. Заходит через SSO (или, если недоступно — сервисным логином/паролем, если разрешено).
   Роль назначается по группе каталога; если ролей нет вовсе — предупреждение в профиле со
   списком нужных групп.
2. «Добавить пакеты» → выбирает менеджер → один из 4 способов → получает результат разбора
   сразу на этой же странице (без перехода): что принято, что уже в базе (с готовой командой
   установки), что не подошло по формату.
3. Открывает карточку заявки (`/requests/{id}`). Пока `request.status == pending` — страница
   **автообновляется каждые 4 секунды**. Как только статус уходит из `pending` (в
   `awaiting_security`/`awaiting_legal`/`quarantined`/`approved`/...) — автообновление
   **останавливается**, дальше — только вручную (кнопка «обновить») или по клику из
   уведомления.
4. По каждому пакету заявки видит: текущий шаг, `blocked_reason`, `next_action` («что делать»),
   команду установки (если уже готова), при раскрытии карточки — весь конвейер шагов, найденные
   уязвимости, находки сканеров содержимого.
5. Если пакет ждёт лицензию — разработчик (или юрист/devsecops/admin) прикладывает ссылку +
   опционально SPDX из выпадающего списка + комментарий (`POST /items/{id}/license-claim`).
   Сервис сохраняет снапшот текста по ссылке для юриста.
6. Ведёт обсуждение — на уровне заявки целиком и отдельно на уровне каждого пакета,
   markdown + упоминания `@логин`, правка/удаление своих сообщений (с пометкой «изменено» после
   `COMMENT_EDIT_WINDOW_MINUTES`).
7. Если пакет упал с технической ошибкой (`failed`) — кнопка «перезапустить проверку»
   (`POST /requests/{id}/retry`) прямо на карточке заявки.
8. Если пакеты больше не нужны (взяли другую библиотеку, переписали код, ошиблись версией) —
   кнопка «закрыть заявку» (`POST /requests/{id}/cancel`). Незавершённые пакеты переходят в
   `cancelled`, заявка уходит из очередей ролей, отказ пишется в журнал. Завершённые пакеты
   не трогаются: отмена не отзывает чужое решение, опубликованный снимает DevSecOps.
9. Узнаёт о решении — через «Профиль» → «Уведомления» (счётчик в сайдбаре) или зайдя в
   карточку заявки вручную. **Никакого проактивного канала вовне сервиса нет** (см. ниже,
   "Что стоит пересмотреть").
10. Получает готовую команду установки (`install_command`) на карточке пакета/в результатах
   проверки — вставляет в свой CI/локальную настройку реестра сам, сервис не пушет в реестр
   потребителя.

## Роль: CI / автоматизация

1. Получает токен — сервисная учётка (`POST /auth/token`, только при `LOCAL_AUTH_ENABLED=true`)
   либо client_credentials Keycloak-клиента. **Токен полноправный — привязан к роли учётки
   целиком**, не к операции (см. `docs/auth.md`, разрыв про отсутствие PAT со scope).
2. `POST /requests` с `Idempotency-Key: ci-<project>-<build-id>` — синхронный ответ `202` сразу
   (заявка создана, конвейер асинхронный).
3. Два варианта дальше:
   - **Неблокирующий** — CI продолжает, статус проверяется отдельно (`GET /requests/{id}`) в
     любой момент, например следующим шагом пайплайна или другим job'ом.
   - **Блокирующий** — `GET /requests/{id}?wait=true&timeout=<1..1800>` держит соединение до
     финального статуса или таймаута; поле `approved` (`true`/`false`) определяет exit-код
     скрипта. Пример готового bash-скрипта — `docs/api.md`.
4. Если пакета ещё нет во внутреннем реестре после ответа — по контракту это означает "не было
   заявки или не прошла модерацию", а не баг конфигурации (см. `migration-from-ci.md`) —
   установка в CI **должна упасть**.

## Роль: Security-инженер / DevSecOps

1. Видит в сайдбаре счётчик очереди `security` + `quarantined`; заходит на «Очередь DevSecOps»
   (`GET /queue/security` — уже отфильтровано по статусам/шагам, отсортировано по времени
   ожидания).
2. По каждой карточке — либо «снять карантин» (если статус `quarantined`, комментарий
   опционален), либо «разрешить»/«отклонить» (если ждёт решения по уязвимостям/баннерам/SAST;
   комментарий обязателен при отклонении).
3. «Разрешить» — фиксирует `security_override_at`/`by`/`comment` на версии пакета, закрывает
   разом обе связанные блокировки (`vuln_scan`/`banner_scan`; `sast_scan` информационный, и
   закрывать по нему нечего), применяется ко всем заявкам с этой версией, конвейер
   возобновляется со скачивания (артефакт был удалён из временного хранилища при отказе —
   перекачивается).
4. «Отклонить» — версия и все ждущие её `request_item` (во всех заявках) переходят в
   `rejected`, артефакты вычищаются из временного хранилища.
5. На карточке пакета (не только в очереди) видит найденные CVE (балл, вектор CVSS,
   `fixed_versions`, ссылка на osv.dev) и находки сканеров содержимого (файл, строка,
   совпадение).
6. Отдельно — «Настройка»: видит состояние снапшота OSV (версия, дата, возраст, устарел ли) и
   может запустить синхронизацию вручную (`POST /admin/osv-sync`); видит состояние
   `worker-go` и сторожа очереди (не требует роли `admin` для чтения — `GET
   /system/status` доступен любой роли, но кнопка «разобрать очередь сейчас» — только `admin`).
7. Может отозвать уже опубликованный пакет (`POST /packages/{version_id}/revoke`) — вне
   зависимости от очереди, по карточке пакета в базе.
8. **Не проверяется системой**: что решающий не является автором заявки, на которую влияет
   решение (см. `docs/ci-parity-gaps.md`, `prevent_approval_by_author`) — UI показывает блок
   решения любому пользователю с ролью `devsecops`, включая случай, когда та же учётка подавала
   заявку.

## Роль: Юрист (legal)

1. Счётчик `legal` в сайдбаре; «Очередь юристов» (`GET /queue/legal`) — только пакеты,
   остановленные на шаге «Лицензия».
2. Если лицензия **ещё не заявлена** разработчиком — карточка это явно показывает
   ("ждём ссылку"), решать нечего.
3. Если заявлена — видит ссылку, SPDX (если указан), кто заявил и когда, комментарий
   разработчика, снапшот текста по ссылке (сворачиваемый блок), и — если у пакета уже была
   подтверждена лицензия для другой его версии — подсказку об этом (`suggested_license`).
4. «Подтвердить» (комментарий опционален) — фиксирует `license_spdx`/`license_source=claim` на
   версии, **предлагает** эту лицензию как рекомендацию для будущих версий того же пакета
   (`package.confirmed_license_spdx`), применяется ко всем заявкам с этой версией, конвейер
   возобновляется со скачивания.
5. «Отклонить» (комментарий обязателен) — версия и все ждущие её `request_item` → `rejected`.
6. Как и у DevSecOps — **нет проверки**, что решающий юрист не автор затронутой заявки.

## Роль: Администратор

1. «Настройка» — все переменные конфигурации, сгруппированные по секциям, только чтение
   (секреты замаскированы). Кнопка «перечитать конфигурацию» (`POST /admin/reload`) —
   перечитывает `blacklist.yml`/`licenses.yml` без рестарта, показывает, сколько правил/лицензий
   загружено.
2. На той же странице — карточка «Обработка очереди»: жив ли worker, сколько пакетов зависло,
   включён ли сторож; кнопка «разобрать очередь сейчас» (`POST /admin/queue-sweep`) — только
   у `admin`.
3. «Аудит-лог» (`/audit`, видна только `admin` в сайдбаре) — кто/что/когда/старое→новое/
   источник по любому действию в системе.
4. Заводит сервисные учётки для CI (`moderctl create-service-account`, только при
   `LOCAL_AUTH_ENABLED=true`) — вне UI, через CLI.
5. Всё, что может `devsecops`/`legal` — тоже может (`admin` проходит любую проверку роли).

## Роль: Аудитор / комплаенс-ревьюер

**Разрыв, не отдельный флоу**: сейчас единственный способ читать `/admin/audit` — иметь роль
`admin` целиком (см. `docs/auth.md`), то есть заодно получить и все административные права
(reload, queue-sweep, все решения). Отдельного read-only флоу для этой роли в текущей
реализации не существует.

## Периферийные роли — точки конфигурации, не интерактивный флоу

Эти роли не "работают" в сервисе день в день — они конфигурируют внешние системы, от которых
сервис зависит, и не имеют отдельного UI-флоу:

| Роль | Точка входа | Что делает |
| --- | --- | --- |
| Владелец Nexus/Artifactory | `.env` (`ARTIFACT_*`) | создаёт/обслуживает hosted-репозитории; `make bootstrap` создаёт их автоматически при первом старте |
| Владелец Keycloak/IdP | Keycloak admin console | realm, группы, маппинг на `ROLE_MAPPING_*` |
| Владелец GitLab-интеграции | GitLab admin/group settings | OAuth-приложение, scope `read_api`/`read_repository` |
| Владелец снапшота OSV | внешний процесс публикации в `ARTIFACT_REPO_OSV` | публикует `osv-pypi.zip` и `osv-npm.zip` по расписанию, сервис только читает |
| Владелец корпоративного прокси | `.env` (`HTTP_PROXY`/`NO_PROXY`) | обслуживает сам прокси вне сервиса |
| SRE / оператор | Prometheus/Grafana, `/api/v1/system/status`, `make run-pending` | наблюдает `/metrics`, диагностирует зависшую очередь |
| Мигрирующая команда | `moderctl import-package-list` (одноразово) | разовый импорт уже одобренных пакетов, дальше — обычный флоу разработчика |

## Что стоит пересмотреть (наблюдения по ходу описания, не решения)

1. **Автообновление карточки заявки останавливается ровно тогда, когда начинается самая долгая
   часть ожидания** — пока конвейер идёт первый раз, статус `pending`, страница обновляется
   каждые 4 с; как только пакет встал в очередь DevSecOps/юристов (то есть неделю может ждать
   решения человека), автообновление выключено. В сочетании с отсутствием внешних уведомлений
   (email/Mattermost) разработчик может не узнать о решении, пока сам не откроет страницу или
   не увидит счётчик в «Профиле».
2. **Самоодобрение технически возможно** и в API, и в UI — ни `decide_security`, ни
   `decide_license`, ни компонент `Actions`/`SecurityBlock`/`LicenseBlock` не проверяют, что
   решающий не является автором затронутой заявки.
3. **Роль `admin` — единственный способ читать аудит-лог** — совмещает "хочу посмотреть
   историю" с "имею право менять конфигурацию/разбирать очередь/принимать решения за любую
   роль". Нет способа выдать только чтение.
4. **CI получает токен уровня учётки, не уровня операции** — единственный способ ограничить,
   что может конкретный пайплайн, сейчас — завести под него отдельную сервисную учётку с нужным
   набором ролей вручную через `moderctl`, не выдать разовый/отзываемый токен с одним
   разрешением.
5. ~~Комментарии могут не создавать уведомления~~ — **проверено, не разрыв**:
   Go API уведомляет автора треда и всех, кого явно упомянули
   через `@логин` (кроме самого пишущего) при каждом новом сообщении.
6. **Периферийные роли не имеют отдельного контракта отказа** — если снапшот OSV устарел,
   прокси недоступен, GitLab OAuth не настроен — сервис деградирует по-разному (шаг 5 → `warn`
   и требует DevSecOps; способ 3 добавления пакетов просто становится недоступен с понятным
   сообщением) — стоит явно решить, устраивает ли это как общий принцип отказоустойчивости для
   всех интеграций разом, а не для каждой по отдельности.
