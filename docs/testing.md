# Тестирование — принципы sentrix, применённые к этому сервису

## Тесты не пишут в целевой Artifactory (прямое решение пользователя)

При проверке сервиса реальными кредами (в т.ч. от продового Artifactory/Sandbox — см.
`docs/ci-parity-gaps.md`, раздел про модель публикации) правило: **весь конвейер выполняется
по-настоящему** — реальное скачивание с upstream-реестра, реальный OSV-скан, реальный banner-
скан, реальный вызов Sandbox — но **шаг `publish` не пишет байты в целевой Artifactory**.

Реализовано как `ARTIFACT_DRY_RUN=true` (`.env`/`app/core/config.py`,
`app/pipeline/steps.py::PublishStep`): при включении шаг публикации не вызывает
`store.publish()`, вместо этого проверяет достижимость/авторизацию через `store.exists()`
(HEAD-запрос — доказывает, что креды рабочие, без записи) и завершает конвейер с `pass` и
пометкой `details.dry_run=true`, **не переводя** заявку/версию в статус `approved` — реального
артефакта по `install_command` нет, ложный "одобрено" был бы хуже честного "не публиковали".

Не применять к SAST/banner-сканированию и остальным шагам 0–7 — они и так не пишут никуда,
кроме своей собственной БД сервиса и временного S3 (MinIO), которое не является целевым
хранилищем и безопасно для тестового прогона.

**SAST включён, но публикацию не блокирует** (прямое решение пользователя) — см.
`docs/ci-parity-gaps.md`, раздел "SAST — включён, но только для отчёта". При тестировании
ожидать по этому шагу результат `info` и находки в отчёте, но НЕ блокировку и НЕ переход
пакета в очередь DevSecOps.

## Три уровня по sentrix (факт, сверено с его кодом/CI)

1. **Юнит** — `*_test.go` рядом с кодом, без внешних зависимостей.
2. **Интеграционные** — тот же `go test ./... -p 1 -count=1`, но против **реального**
   Postgres/SeaweedFS (`docker compose up -d postgres seaweedfs`), не моков — используют
   `internal/testutil` (`pg_lock.go`, `counting_server.go`).
3. **E2E** — отдельный build tag (`//go:build e2e`), исключён из обычного `go test ./...`,
   гоняется отдельной командой (`go test -tags=e2e ./e2e/...`) против **реально собранного и
   запущенного бинарника** (`docker-compose.integration.yml` поднимает сервис как настоящий
   процесс и бьёт по нему по HTTP; в CI этот override ещё и сбрасывает публикуемые порты, чтобы
   параллельные пайплайны не конфликтовали).

Ключевой принцип, ради которого это всё: **на каждом уровне выше юнит-тестов — настоящая
инфраструктура, не мок**. Мок Postgres/S3 может годами молча расходиться с реальным поведением;
реальный Postgres в CI эту возможность убирает физически.

## Как сейчас в moderation-repo (Python) — сверено с кодом, не предположение

`backend/tests/conftest.py` устанавливает для **всех** тестов (unit, integration, "e2e" —
папки называются по-разному, но фикстуры — общие): `DATABASE_URL=sqlite://`,
`CELERY_TASK_ALWAYS_EAGER=true`, плюс подмену всех внешних адаптеров на fake/in-memory
реализации (`InMemoryObjectStorage`, `set_artifact_store`, `set_vuln_index`, `set_notifier`,
`set_scanners`). Ни один из трёх каталогов тестов (`tests/unit`, `tests/integration`,
`tests/e2e`) не бьёт по реальному Postgres, реальному брокеру или реально запущенному процессу
сервиса — `backend/tests/e2e/test_main_flow.py`, несмотря на название, гоняет конвейер **в
одном процессе pytest** через FastAPI `TestClient`-подобный `api`-фикстуры и fake-адаптеры, не
через реально поднятый Docker-стек.

Это не значит, что тесты плохие — они полезны и достаточно строгие для доменной логики
(конвейер, resume, sibling-propagation и т.д. покрыты). Но это **не то же самое**, что три
уровня sentrix: здесь один структурный уровень (быстрый, детерминированный, полностью
изолированный от инфраструктуры), а не три уровня с растущей близостью к реальности. Раздутая
структура директорий (`unit`/`integration`/`e2e`) создаёт впечатление многоуровневости, которой
по факту нет — стоит либо привести к сентриксовому смыслу, либо явно переименовать уровни во что
то не вводящее в заблуждение, если оставлять как есть до переноса на Go.

## Целевая модель для Go-версии

Прямое применение трёх уровней sentrix, без изменений философии:

1. **Юнит** — доменная логика без сети/БД: разбор `package_list`-записей, конвейерные переходы
   (`StepOutcome`), policy engine (blacklist/quarantine/license), `siblings_awaiting` —
   именно то, что уже хорошо покрыто в Python-версии, переносится как тестовые случаи (не как
   код теста, как *сценарии*).
2. **Интеграционные** — реальный Postgres (golang-migrate применяет миграции перед прогоном,
   как в sentrix), реальный NATS+Valkey (не in-memory очередь), реальный SeaweedFS. В отличие от
   текущей Python-версии, здесь **не будет** SQLite-облегчения — pgx работает только с Postgres,
   и это осознанно правильно: SQLite-подмена в Python была удобством SQLAlchemy, не архитектурным
   принципом, переносить её эквивалент на Go не нужно и вредно (см. `architecture.md`, "Типы
   намеренно переносимые" — это была уступка ради скорости unit-тестов, а не часть контракта).
3. **E2E** — отдельный build tag, реально собранный Go-бинарник, реальный HTTP, включая OIDC
   против настоящего (тестового) Keycloak-контейнера — не заглушки токенов. Golden-file сценарии
   из `migration-to-go.md` ("Стратегия тестирования переноса") — это фактически e2e-уровень,
   написанный один раз и переиспользуемый и для проверки переноса, и как постоянный regression
   suite после.

## Дифференциальная проверка против эталона

Там, где мы реализуем чужие правила, свои тесты проверяют наше понимание правил, а не сами
правила. Для версий это особенно опасно: semver и PEP 440 полны исключений, о которых узнаёшь
только когда они уже стоили инцидента.

Поэтому `backend-go/internal/version` проверяется не только таблицами, но и прогоном против
эталонных реализаций — `packaging` (PEP 440) и `semver` (npm). Корпус собирается из настоящих
реестров: требования берутся из метаданных популярных пакетов, версии — из их истории релизов.

```bash
cd backend-go
# корпус (нужны packaging и npm-пакет semver)
VERCHECK_OUT=/tmp/vercheck python internal/version/vercheck/gen_pypi.py
VERCHECK_OUT=/tmp/vercheck python internal/version/vercheck/gen_pypi_cmp.py
SEMVER_PATH=$(node -p "require.resolve('semver')") VERCHECK_OUT=/tmp/vercheck \
  node internal/version/vercheck/gen_npm.mjs

go run ./internal/version/vercheck /tmp/vercheck/pypi_cases.json   pypi
go run ./internal/version/vercheck /tmp/vercheck/pypi_compare.json pypi compare
go run ./internal/version/vercheck /tmp/vercheck/npm_cases.json    npm
go run ./internal/version/vercheck /tmp/vercheck/npm_compare.json  npm compare
```

Последний прогон: pypi — 73 200 пар «требование/версия» и 6 537 сравнений, npm — 2 185 500 пар и
4 349 сравнений, расхождений нет. Проверка нашла два настоящих расхождения, оба исправлены:
правило PEP 440 про строгие сравнения («<2.0» не допускает 2.0.0a1) и оператор, отделённый от
версии пробелом («>= 0.3.0»), которых в npm тысячи.

В CI это не прогоняется: нужен интернет и два чужих рантайма. Прогонять — при правке
`internal/version`.

## Что взять из Python-тестов как сценарии (не как код)

Существующие фикстуры/сценарии — ценный актив независимо от языка: `tests/e2e/test_main_flow.py`
(happy path pypi от заявки до install-команды), `tests/unit/test_parallel_approvals.py`
(sibling-propagation), `tests/unit/test_queue_watchdog.py`/`test_queue_doctor.py` (защита от
зависания очереди — переносится как поведенческий контракт для NATS/Valkey-версии),
`tests/unit/test_task_publishing.py` (тот самый Celery `current_app`-thread-local баг,
задокументированный в `architecture.md` как "Задачи ставятся только через `publish`" — в Go эта
конкретная ловушка не воспроизводится, потому что NATS-клиент не имеет thread-local
"текущего приложения" по конструкции, но стоит явно перепроверить, что новый транспорт не
привносит свой аналог такой ловушки, а не считать проблему исчезнувшей молча).

## Порог покрытия

Python-версия — `pytest-cov`, `--cov-fail-under=70` (`pyproject.toml`). Явного порога у sentrix
в инвентаризации не найдено — решить отдельно для Go-версии (внести в `.golangci.yml`/CI-джобу
`test:lint`, как у sentrix, или отдельным шагом `go test -cover`).
