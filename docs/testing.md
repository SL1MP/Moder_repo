# Тестирование — принципы sentrix, применённые к этому сервису

## Тесты не пишут в целевой артефактори

Для проверки с реальными учётными данными используется `ARTIFACT_DRY_RUN=true`.
Конвейер скачивает пакет, выполняет настроенные проверки и пишет служебные данные,
но шаг `publish` не переносит пакет в целевой репозиторий и не выставляет ложный
статус `approved`. Реализация находится в `backend-go/internal/pipeline` и
`backend-go/internal/artifactstore`.

## Три уровня по sentrix (факт, сверено с его кодом/CI)

1. **Юнит** — `*_test.go` рядом с кодом, без внешних зависимостей.
2. **Интеграционные** — тот же `go test ./... -p 1 -count=1`, но против **реального**
   Postgres (`docker compose up -d db`), не моков — используют
   `internal/testutil` (`pg_lock.go`, `counting_server.go`).
3. **E2E** — отдельный build tag (`//go:build e2e`), исключён из обычного `go test ./...`,
   гоняется отдельной командой (`go test -tags=e2e ./e2e/...`) против **реально собранного и
   запущенного бинарника** (`docker-compose.integration.yml` поднимает сервис как настоящий
   процесс и бьёт по нему по HTTP; в CI этот override ещё и сбрасывает публикуемые порты, чтобы
   параллельные пайплайны не конфликтовали).

Ключевой принцип, ради которого это всё: **на каждом уровне выше юнит-тестов — настоящая
инфраструктура, не мок**. Мок Postgres/S3 может годами молча расходиться с реальным поведением;
реальный Postgres в CI эту возможность убирает физически.

## Текущая модель Go-тестов

1. **Юнит** — доменная логика без внешней сети и БД, `*_test.go` рядом с кодом.
2. **Интеграционные** — настоящий PostgreSQL через `MODERATION_TEST_POSTGRES_DSN`;
   миграции применяются до прогона.
3. **E2E** — собранный Go-бинарник и реальные HTTP-запросы к тестовому стеку.

## Одна база на все пакеты: прогон только `-p 1`

Интеграционные тесты go-версии ходят в общий Postgres, и часть из них проверяет состояние
сервиса целиком, а не только своей строки: «после захвата очередь пуста», «активная версия
снапшота ровно одна», «сторож не трогает живой прогон». Такие проверки по-другому и не
написать — именно это поведение и есть предмет теста.

Отсюда правило: с базой прогон идёт `go test -p 1 ./...`. По умолчанию go гоняет пакеты
параллельно, и тогда тесты видят строки друг друга — падает не код, а тест, причём
невоспроизводимо поодиночке. Это уже стоило нескольких ложных разборов.

## Дифференциальная проверка против эталона

Там, где мы реализуем чужие правила, свои тесты проверяют наше понимание правил, а не сами
правила. Для версий это особенно опасно: semver и PEP 440 полны исключений, о которых узнаёшь
только когда они уже стоили инцидента.

Поэтому `backend-go/internal/version` проверяется не только таблицами, но и прогоном против
эталонных реализаций — `packaging` (PEP 440) и `semver` (npm). Корпус собирается из настоящих
реестров: требования берутся из метаданных популярных пакетов, версии — из их истории релизов.

```bash
cd backend-go
# корпус (нужны packaging и npm-пакет semver)
VERCHECK_OUT=/tmp/vercheck python internal/version/vercheck/gen_pypi.py
VERCHECK_OUT=/tmp/vercheck python internal/version/vercheck/gen_pypi_cmp.py
SEMVER_PATH=$(node -p "require.resolve('semver')") VERCHECK_OUT=/tmp/vercheck \
  node internal/version/vercheck/gen_npm.mjs

go run ./internal/version/vercheck /tmp/vercheck/pypi_cases.json   pypi
go run ./internal/version/vercheck /tmp/vercheck/pypi_compare.json pypi compare
go run ./internal/version/vercheck /tmp/vercheck/npm_cases.json    npm
go run ./internal/version/vercheck /tmp/vercheck/npm_compare.json  npm compare
```

Последний прогон: pypi — 73 200 пар «требование/версия» и 6 537 сравнений, npm — 2 185 500 пар и
4 349 сравнений, расхождений нет. Проверка нашла два настоящих расхождения, оба исправлены:
правило PEP 440 про строгие сравнения («<2.0» не допускает 2.0.0a1) и оператор, отделённый от
версии пробелом («>= 0.3.0»), которых в npm тысячи.

В CI это не прогоняется: нужен интернет и два чужих рантайма. Прогонять — при правке
`internal/version`.

## Порог покрытия

Явный обязательный процент покрытия пока не установлен. Его следует закрепить в CI
отдельным шагом `go test -cover`, не смешивая с форматированием и `go vet`.
