# Аутентификация и пользователи

Начиная с миграции `0023_auth_sessions` пользователи, права и сессии
принадлежат приложению, а Keycloak/OIDC только подтверждает личность.

## Способы входа

### Локальный пользователь

1. Администратор создаёт пользователя в `Настройка → Пользователи и роли`.
2. Пароль хешируется Argon2id (`64 MiB`, `t=1`, `p=4`) и открытым не хранится.
3. `POST /api/v1/auth/token` проверяет DB-throttle: 7 ошибок на логин или 30
   ошибок с IP за 15 минут. Блокировка начинается с минуты и растёт до 30 минут.
4. При успешном входе backend выдаёт короткий access JWT (15 минут) и случайный
   refresh-токен (30 дней). В БД хранится только SHA-256 refresh-токена.
5. Refresh-токен одноразовый: `POST /api/v1/auth/refresh` атомарно отзывает его
   и выдаёт новую пару.

Для совместимости существующие bcrypt-хэши читаются. Новый или изменённый
пароль всегда сохраняется в Argon2id. Флаг `must_change_password` закрывает
остальной интерфейс до успешной смены временного пароля.

### OIDC / Keycloak

OIDC настраивается администратором в `Настройка → OIDC / Keycloak`; пересборка
и перезапуск не нужны. Переменные `OIDC_*` только впервые заполняют пустую
строку настроек в БД.

Для унаследованного compose-варианта с двумя адресами сохранена совместимость:
если runtime issuer совпадает с `OIDC_PUBLIC_ISSUER`, discovery/JWKS и обмен
code выполняются по внутреннему `OIDC_ISSUER`, а authorization endpoint и claim
`iss` проверяются по публичному. При изменении issuer через web этот legacy-
режим автоматически перестаёт применяться.

1. Браузер открывает `/api/v1/auth/oidc/login`.
2. Backend создаёт `state`, `nonce` и PKCE verifier, подписывает их и кладёт в
   `HttpOnly; SameSite=Lax` cookie на 10 минут.
3. После Keycloak callback backend сверяет cookie/state, обменивает code с PKCE,
   проверяет подпись ID token по JWKS, issuer, audience и nonce.
4. Пользователь ищется только по неизменяемой паре `(source=oidc, subject=sub)`.
   При первом входе строка создаётся автоматически без ролей. Совпадение логина
   с локальной учёткой не связывает их молча.
5. Backend выдаёт ту же внутреннюю access/refresh-пару, что при локальном входе,
   и возвращает её SPA во fragment `/oidc/callback#...`. Токены Keycloak в SPA
   и в API сервиса не используются.

В Keycloak зарегистрируйте redirect URI, показанный на странице настройки:
`<PUBLIC_BASE_URL>/api/v1/auth/oidc/callback`.

### Корпоративный Keycloak и внутренний CA

Если корпоративный Keycloak опубликован с сертификатом внутреннего центра
сертификации, одного `OIDC_ISSUER` недостаточно: минимальный образ backend не
знает корпоративный Root CA. Сервис поддерживает дополнительный trust store,
который применяется ко всему серверному OIDC-flow:

- discovery (`/.well-known/openid-configuration`);
- обмен authorization code на токены;
- загрузка и ротация JWKS.

Публичные CA при этом не заменяются — корпоративные сертификаты добавляются к
системному набору. Для Docker Compose:

1. Создайте каталог `certs/ca`.
2. Положите туда публичные Root и Issuer CA в PEM-формате с расширением
   `.crt`, `.cer` или `.pem`. Закрытый ключ не нужен.
3. Оставьте `CA_CERTS_HOST=./certs/ca` либо укажите абсолютный каталог хоста.
4. Пересоздайте `api-go`, чтобы процесс перечитал trust store:

```bash
sudo docker compose up -d --no-deps --force-recreate api-go
sudo docker compose logs --tail=100 api-go
```

В контейнере Compose всегда задаёт `CA_CERTS=/etc/moderation/ca`; значение
`CA_CERTS` из `.env` используется только при локальном запуске Go-процесса без
Docker. Пустой каталог означает доверие только системным CA. Несуществующий
путь или повреждённый сертификат останавливает backend при старте с явной
ошибкой `корпоративные CA не загружены`.

На стороне корпоративного Keycloak нужен OIDC-клиент:

| Параметр | Значение |
|---|---|
| Client ID | значение `OIDC_CLIENT_ID`, обычно `moderation-web` |
| Standard flow | включён |
| PKCE | `S256` |
| Valid redirect URI | `https://<адрес-сервиса>/api/v1/auth/oidc/callback` |
| Web origin | `https://<адрес-сервиса>` |
| Client authentication | выключена для public client или включена вместе с `OIDC_CLIENT_SECRET` |

Issuer, Client ID, secret, публичный адрес сервиса и подпись кнопки по-прежнему
меняются в `Настройка → OIDC / Keycloak` и применяются без перезапуска. CA —
файл уровня развёртывания, поэтому перечитывается при старте `api-go`.

Пользователь должен существовать в корпоративном realm либо приходить в него
из подключённого LDAP/AD. После первого успешного SSO сервис автоматически
создаёт свою локальную запись по `sub`, но не копирует права из групп
Keycloak: роли модерации назначаются администратором внутри сервиса.

## Создание и изменение пользователей

- Через web/API заранее создаются только локальные пользователи.
- OIDC-пользователь создаётся только при первом успешном SSO.
- Поля `username`, `email`, `description`, активность и роли хранятся в Postgres.
- `is_superuser` соответствует роли `admin`; сервис синхронизирует их.
- Нельзя отключить или разжаловать последнего активного администратора.
- Пароль OIDC-пользователя изменить в сервисе нельзя — им управляет IdP.
- Первый локальный администратор создаётся только в пустой базе из
  `ADMIN_USERNAME`/`ADMIN_PASSWORD` (по умолчанию `admin/admin`). Bootstrap
  не выставляет обязательную смену: пароль нужно сменить
  сразу либо задать безопасным до первого запуска.

## Персональные API-токены

В профиле пользователь может выпустить PAT вида `dso_pat_<random>`. Открытое
значение показывается один раз, в БД хранится только SHA-256. PAT действует от
имени владельца с его текущими ролями, может иметь срок и отзывается отдельно.

Защищённый API также принимает Bearer JWT доверенного OIDC-провайдера. Такой
запрос создаёт OIDC-пользователя по `sub`, если его ещё нет;
права всё равно читаются из Postgres, а не из групп токена. Браузерный вход
всегда завершает flow внутренней access/refresh-сессией.

```bash
curl -H 'Authorization: Bearer dso_pat_...' \
  https://moderation.example/api/v1/auth/me
```

## Основные переменные первичного запуска

```dotenv
LOCAL_AUTH_ENABLED=true
LOCAL_AUTH_SECRET=<случайный секрет подписи внутренних access JWT>
LOCAL_AUTH_TOKEN_TTL_MINUTES=15
LOCAL_REFRESH_TOKEN_TTL_HOURS=720
ADMIN_USERNAME=admin
ADMIN_PASSWORD=admin

OIDC_ENABLED=false
OIDC_ISSUER=https://keycloak.example/realms/company
OIDC_CLIENT_ID=moderation-web
OIDC_CLIENT_SECRET=
OIDC_PUBLIC_BASE_URL=https://moderation.example
OIDC_BUTTON_LABEL=Войти через Keycloak
```

После первого запуска OIDC меняется через web. `LOCAL_AUTH_SECRET` должен быть
одинаковым на всех репликах и не должен меняться без необходимости: смена
немедленно завершит все access-сессии (refresh-сессии смогут получить новый).
