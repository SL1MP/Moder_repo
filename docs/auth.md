# Аутентификация — приведение к единой модели с sentrix/oakshield/vm.service

Текущая реализация (`backend/app/core/security.py`, `backend/app/api/deps.py`) — сверена с
кодом, факты ниже точные, не предположения. Задача этого документа — свести три референсных
подхода (см. `../../CLAUDE.md`-инвентаризацию в истории проекта) и текущую реализацию к одной
модели, которую примет и Go-версия (`migration-to-go.md`).

## Как сейчас (moderation-repo, Python)

- Основной путь — OIDC Authorization Code + PKCE к Keycloak: SPA получает токен, API проверяет
  подпись по JWKS издателя (RS256/ES256), принимает и внутренний, и публичный issuer.
  Роли — маппинг групп каталога через `ROLE_MAPPING_*` (статично, переменными окружения).
- Fallback — `LOCAL_AUTH_ENABLED` (в прод `false`): сервисной учётке выдаётся **плоский
  self-signed JWT** (HS256, секрет `LOCAL_AUTH_SECRET`), TTL фиксированный
  (`LOCAL_AUTH_TOKEN_TTL_MINUTES`, 480 мин по умолчанию), без refresh, без ротации, без отзыва
  по одному токену — только целиком через отключение учётки.
- Пароли — bcrypt (72-байтный лимit обработан явно).
- RBAC — четыре плоские роли (`admin`/`devsecops`/`legal`/`developer`), `admin` — суперпозиция
  прав, проверка на стороне API (`require_roles`), не только в UI.
- **Нет защиты от подбора пароля** — `verify_password` вызывает `bcrypt.checkpw` напрямую, без
  счётчика неудачных попыток, без лока по аккаунту/IP.
- `audit_log` фиксирует действия администратора (reload, revoke, queue-sweep и т.д.), но
  **`sync_user()` молча обновляет `user.roles` при каждом логине** по claims из токена — смена
  роли пользователя из-за изменения членства в группе каталога **не попадает в `audit_log`**,
  видна только как побочный эффект следующего логина.
- Чтение аудита (`GET /api/v1/admin/audit`) требует полной роли `admin` — нет более узкой
  read-only возможности.

## Как у референсов (факты, не интерпретация)

| | sentrix | oakshield (DSO-track) | vm.service |
| --- | --- | --- | --- |
| Браузер | локальный bcrypt + опциональный OIDC (не протестирован с реальным IdP) | OIDC Authorization Code+PKCE (Keycloak) | OIDC (Keycloak) |
| CI/автоматизация | API-токены (отдельно от пользовательских сессий) | **PAT** — `dso_pat_<b64url32>`, хранится как SHA-256, показывается один раз | scoped CI-токены, ограничены "version group" |
| Локальный пароль | bcrypt, server-side сессии (24ч) | Argon2, DB-throttle (7/аккаунт или 30/IP за 15 мин → удваивающийся lockout) | — (везде OIDC) |
| Защита от перебора | `MaxFailedLoginAttempts=10`, `LockoutDuration=15m`, **constant-time dummy-compare** против username-enumeration по времени ответа | DB-throttle с удвоением | dev-only bypass (`/auth/dev-login`, только при `ENVIRONMENT=dev`) |
| RBAC | роли есть, детали не в фокусе инвентаризации | иерархия `reader<writer<maintainer<owner` + `RoleNone` (явный deny) + superuser | роли per "project group" |
| Аудит прав | — | **`access_audit`**, отдельный `GET /api/access-audit`, не требует полного admin | — |
| Секрет для локальных токенов | нет — сессии server-side, не self-signed JWT | нет (PAT — случайный токен, не JWT) | JWT, секрет есть |

## Целевая модель для moderation-repo (и её Go-версии)

Сводится к трём методам, разрешаемым по порядку — как у oakshield, это самый чистый вариант из
референсов:

1. **OIDC Authorization Code + PKCE** (браузер, SPA) — без изменений, уже реализовано верно.
2. **PAT — персональный/сервисный токен с ограниченной областью действия** (CI/автоматизация)
   — заменяет текущий плоский local-JWT для сервисных учёток:
   - случайный токен (`modsvc_pat_<b64url32>`), хранится как SHA-256-хэш, показывается один раз
     при выдаче (как у oakshield);
   - привязан к **набору разрешений**, не к роли целиком — минимум: "создавать заявки и читать
     их статус", без доступа к решениям (карантин/лицензия/безопасность) даже если у
     выпустившей его учётки эти права есть;
   - отзывается по одному токену, не только целиком через отключение учётки — снимает разрыв
     "владелец CI-интеграции хочет отозвать токен одного пайплайна" из `user-stories.md`;
   - опциональный срок действия при выпуске, без обязательного TTL/refresh — это долгоживущий,
     но узкий по правам токен, не сессия.
   - убирает нужду в `LOCAL_AUTH_SECRET` как таковом — токен не подписывается общим секретом,
     сравнение идёт по хэшу в БД.
3. **Локальный пароль — только bootstrap/break-glass**, не общий способ для CI (для CI — PAT):
   - `LOCAL_AUTH_ENABLED=false` в проде по умолчанию — без изменений;
   - назначение сужается явно: вход администратора при недоступном/ещё не настроенном Keycloak,
     не постоянный способ входа для сервисных учёток;
   - вместо self-signed JWT с `LOCAL_AUTH_SECRET` — **server-side сессии**, как в sentrix:
     случайный opaque-токен сессии, хранится (хэш) в БД с TTL, отзывается явно. Убирает
     статический секрет из конфигурации целиком (риск, отмеченный в `architecture.md`, снимается
     не валидацией дефолта, а удалением самого механизма, которому нужен статический секрет).
   - добавить защиту от перебора: DB-backed throttle (числа — можно взять готовые у oakshield:
     7 попыток/аккаунт или 30/IP за 15 минут, удваивающийся lockout) **плюс** constant-time
     dummy-hash compare из sentrix — обе техники не взаимоисключающие, закрывают разные векторы
     (перебор и username-enumeration по времени ответа).
   - пароли — рассмотреть переход bcrypt → Argon2id (рекомендация oakshield, самая свежая из
     референсов); не блокирующее решение, можно сделать отдельным шагом.

### RBAC — без структурных изменений, один точечный разрыв закрыть

Плоская модель `admin`/`devsecops`/`legal`/`developer` подходит домену лучше, чем иерархия
oakshield (`legal`/`devsecops` — равнозначные специализации, не под-/над-роли друг друга) —
менять не нужно. Добавить:

- **`auditor`** — пятая роль, read-only: доступ только к `GET /api/v1/admin/audit` и истории
  `pipeline_step`/`comment` без прав на решения. Закрывает разрыв "аудитор сейчас требует полной
  роли `admin`" из `stakeholders.md`. Реализация — тот же паттерн `require_roles`, что уже есть,
  без новой архитектуры.
- **Аудит смены ролей** — `sync_user()` должен писать в `audit_log`, когда роли пользователя
  меняются по сравнению с предыдущим значением (не только когда меняет их администратор вручную)
  — сейчас это единственный путь изменения прав, не оставляющий следа.

## Что из этого можно сделать уже в Python-прототипе, не дожидаясь переноса на Go

Три вещи не связаны с языком реализации и дёшевы уже сейчас, если приоритет — закрыть реальный
риск раньше, чем закончится перенос на Go:

1. Аудит смены ролей в `sync_user()` — несколько строк.
2. DB-backed throttle на `verify_password`/`/auth/token` — новая таблица (аналог
   `login_throttle`) + миграция.
3. Роль `auditor` — новая строка в `ROLE_TITLES`/проверках, без изменения модели данных.

PAT-механизм и замена local-JWT на server-side сессии — крупнее, логично делать сразу в
Go-версии как часть `migration-to-go.md`, а не дважды.

## Открытый вопрос

Замена bcrypt → Argon2id — делать при переносе на Go (там нет уже написанного кода, который
жалко переписывать) или оставить bcrypt (используется в 2 из 3 референсов, тоже приемлемо)?
Не блокирует остальное — можно решить отдельно.
