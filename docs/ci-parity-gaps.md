# Разрыв с функциональностью CI-версии (pt-package-review/moderated)

Явный трекинг, чтобы при переносе на Go ничего не потерялось молча. "CI-версия" — три
GitLab-репозитория, которые сейчас (на момент написания) реально в проде: `pt-package-review`
(Python CLI), `moderated` (GitLab CI templates), `moderation-security-policy-project` (GitLab
native security policy). Self-service прототип (`moderation-repo/`, эта папка) — не тонкий
порт CI-версии, а осознанный редизайн модели работы (см. `README.md`, "Что сервис намеренно не
делает") — часть разрывов ниже это следствие сознательного решения, не недосмотра. Каждый пункт
помечен явно.

Полная построчная инвентаризация CI-версии — `../moderation-service/docs/user-stories.md`
(Epic 1–15, там же ссылки на конкретный код `pt-package-review`/`moderated`).

## Артефактори — production это JFrog Artifactory, не Nexus, и модель публикации другая

**Подтверждено по коду**: CI-версия (`pt-package-review`) работает исключительно с **JFrog
Artifactory** (`DEVOPS_ARTIFACTORY_URL=https://repo.ptsecurity.ru/artifactory`) — AQL-поиск
(`api/search/aql`), copy API (`api/copy/{source_repo}/{src_path}?to=/{moderated_repo}/{dst_path}`),
reindex (`api/{repo_type}/{repo}/reindex`), storage-метаданные (`api/storage/{repo}/{path}`),
менеджер-специфичные virtual-эндпоинты (`api/npm/{repo}`, `api/pypi/{repo}/simple`,
`api/nuget/{repo}`, `api/conan/{repo}`). Nexus в production **не используется вообще** — это
были мои собственные предположения при локальной проверке (см. предыдущую сессию), не факт о
реальной системе. `ArtifactStore` в прототипе поддерживает Artifactory через
`GenericArtifactStore` (`ARTIFACT_STORE=generic`) — именно этот адаптер, не `NexusArtifactStore`
(дефолт в `.env.example`), должен быть основным ориентиром при верификации и при переносе на Go.

**Более существенное расхождение — сама модель публикации, не только выбор системы**:

- **CI-версия**: пакет никогда не проходит через процесс `pt-package-review` как байты.
  `install_packages`/`--get-diff` заставляет нативный инструмент менеджера (`pip download`,
  `npm view`+`wget`, `go mod download`, `mvn`, `conan download`) скачать пакет **через
  Artifactory как прокси** (remote-репозиторий, кэширующий upstream). Это кладёт байты в
  **кэш Artifactory**. Публикация (`--publish`) — **server-side copy** внутри Artifactory
  (`api/copy/...`) из кэш-репозитория в moderated-репозиторий. CI-процесс ни разу не держит
  файл пакета у себя и не делает `PUT` — только запускает копирование средствами самого
  Artifactory.
- **Self-service прототип**: `GenericArtifactStore.publish()` (`app/adapters/artifact_store.py`)
  скачивает пакет **напрямую с публичного upstream-реестра** (`pypi.org`/`registry.npmjs.org`/
  ...) в процесс сервиса, кладёт во временное S3-хранилище (MinIO), затем делает **`PUT` с
  сырыми байтами** на собранный по шаблону путь (`ARTIFACT_PATH_TEMPLATE_*`) — Artifactory
  здесь используется как обычное hosted-хранилище, а не как кэширующий прокси с
  server-side copy.

**Почему это не просто деталь реализации:**

1. **Неизвестно, разрешает ли реальный production Artifactory прямой `PUT`** в moderated-
   репозитории. Если они (как часто бывает в more curated setups) сконфигурированы так, что
   контент туда попадает только через copy из доверенного кэш-репозитория — прямой `PUT` от
   имени сервиса может быть отклонён политикой/правами (403/401), даже если базовая
   аутентификация верна. Это ровно тот класс проблемы, который я уже словил с Nexus (EULA-гейт
   молча превращал корректно аутентифицированные запросы в 403) — здесь тот же риск, но
   непроверяемый без доступа к реальному инстансу.
2. **Путь хранения файла определяет сам Artifactory** (конкретный layout для pypi/npm/nuget
   remote-репозитория, зависящий от типа репозитория), а не жёстко заданный шаблон
   `{repo}/{name}/{filename}` — эти пути могут не совпасть с тем, что реально ожидает
   Artifactory для этого типа репозитория, из-за чего `PUT` может лечь не туда, куда ожидается
   при последующем чтении через `pip install -i .../simple`.
3. **Обход собственного кэша Artifactory** — прототип каждый раз идёт в публичный upstream
   напрямую, не используя remote-репозиторий как прокси-кэш, который CI-версия уже использует
   и логически предполагает существующим (иначе зачем в реальной инфраструктуре вообще
   настроены remote-репозитории). Не переиспользовать существующую инфраструктуру кэширования —
   не ошибка сама по себе, но стоит explicit-но решить, осознанный ли это выбор.

**Требует явного решения, не тихого предположения**: оставить модель "скачать + PUT" как
осознанно более простую и слабо связанную (не зависящую от того, как настроены remote-репозитории
у конкретного заказчика), либо перепроектировать `ArtifactStore` под реальную модель
(AQL-поиск в кэш-репозитории + copy API) — что сближает поведение с CI-версией, но привязывает
сервис к конкретной топологии Artifactory-репозиториев (кэш + moderated на менеджер), которую
нужно будет знать заранее, а не только адрес и токен.

## Пакетные менеджеры — все 10 обязательны, не бэклог "по мере необходимости"

**Статус (прямое замечание пользователя, зафиксировано жёстко)**: поддержка всех видов
модерации — обязательный скоуп self-service сервиса, не список "добавим, если понадобится".
CI-версия (`pt-package-review`) закрывает 10 менеджеров; self-service прототип — 4
(`pypi`/`npm`/`go`/`nuget`, `backend/app/managers/`). Пока не реализованы **6**: maven, docker,
conan, terraform, luarocks, general (произвольный URL+sha256) — каждый из них уже кем-то
используется в CI-версии, значит каждый добавляет реальный "вид модерации", который
self-service сервис пока не может заменить, — до полного покрытия сервис не может считаться
полной заменой CI-версии, только частичной.

**Предлагаемый порядок реализации** (не окончательный — приоритет ниже Docker/Sandbox из
предыдущих решений, между собой упорядочены по сложности переноса, от простого к сложному):

1. **General** — самый простой: верификация по `url@sha256:<digest>`, без обращения к
   специфичному реестру пакетов. Хорошая "разминка" для первого нового плагина после текущих 4.
2. **Maven** — обычный REST API (Sonatype `solrsearch`) + разбор POM, без специфичных бинарных
   зависимостей на CI-хосте.
3. **Nuget** уже есть — Terraform по сложности похож (сверка SHA-256 по OS/arch, обнаружение
   provider API через `.well-known/terraform.json`) — не требует внешних CLI-инструментов.
4. **Luarocks** — требует `luarocks` CLI на хосте/в контейнере сервиса (shell out), чуть сложнее
   из-за внешней зависимости, но логика проверки простая.
5. **Docker** — уже приоритет №1 по отдельному решению (см. ниже) — специфика: multiarch-
   манифесты, `skopeo`.
6. **Conan** — самый сложный: граф зависимостей (`conan graph build-order`), quarantine-safe
   замена версий, патчи, требует `conan` CLI.

Это черновой порядок для планирования, не жёсткий график — при реализации в Go (фаза 3,
`docs/migration-to-go.md`) можно и нужно уточнять по факту, если какой-то менеджер понадобится
раньше по внешней причине (как уже произошло с Docker и Sandbox).

- **Docker — приоритет №1 среди недостающих (прямой запрос пользователя)**: конкретная причина
  — образы тяжёлые, повторное скачивание/pull того, что уже одобрено и лежит во внутреннем
  реестре, ощутимо дороже, чем для остальных менеджеров, поэтому "найти уже закачанное вместо
  того чтобы тянуть заново" здесь особенно важно. Механизм для этого уже есть и работает для
  4 текущих менеджеров — «База пакетов» (`GET /packages`, UI-страница `PackagesBase.tsx`) и
  `POST /packages/check` (способ 4 на странице «Добавить пакеты», `docs/flows.md`, шаг
  разработчика №2) — но и dropdown менеджера на странице, и backend жёстко ограничены
  `pypi`/`npm`/`go`/`nuget` (`PackagesBase.tsx`: `<option value="pypi">...`, без docker).
  Добавление Docker как менеджера автоматически включает его и в этот поиск — отдельного UI не
  требуется, только реализация плагина + добавление пункта в dropdown. Что переносить из
  CI-версии: проверка multiarch-манифестов (`manifest.list.v2+json`/`oci.image.index.v1+json`),
  сверка digest с реестром (в т.ч. digest platform-манифеста), обработка `403 features are a
  Pro` от Docker Hub, публикация через `skopeo copy --all` (сохраняет fat manifest).
- **Conan** — разрешение графа зависимостей (`conan graph build-order`, Linux+Windows профили),
  поиск quarantine-safe замены версии вместо блокировки, патчи
  (`name@version:custom_patches/<product>/<pkg>/<ver>/<patch_file>`), внутренизация source URL
  в `conandata.yml`.
- **Terraform** — сверка SHA-256 каждого OS/arch-дистрибутива с upstream registry API,
  обнаружение provider API через `.well-known/terraform.json`.
- **Maven** — Sonatype `solrsearch` для даты публикации, извлечение `issueManagement`/`scm` из
  POM, догрузка Gradle Module Metadata classifier-артефактов.
- **Luarocks** — `luarocks search --porcelain`, публикация через `luarocks pack` +
  `python-artifactory`.
- **General** — верификация произвольного URL по `url@sha256:<digest>`, спецлогика для
  `github.com`/`hashicorp-releases.yandexcloud.net`.

**Важно для схемы БД**: миграция `0001_initial_schema` (и Python, и уже перенесённая
Go-версия в `backend-go/migrations/`) хардкодит `CHECK (manager IN ('pypi', 'npm', 'go',
'nuget'))` на трёх таблицах. Это **сознательно не расширено сейчас** — добавление менеджера
без реализации его плагина бессмысленно — но это прямая точка, которую нужно трогать новой
миграцией (не правкой `0001` задним числом, см. урок из `0004` про CHECK-константы) при
добавлении каждого нового менеджера.

## Обнаружение транзитивных зависимостей

**Подтверждено по README прототипа**: осознанно не реализовано — "Не подтягивает транзитивные
зависимости: проверяется и публикуется только сам заявленный пакет". В CI-версии есть режим
`--find-dependencies` (строит граф и добавляет найденные зависимости в
`package_list.txt`/коммитит). Модель самого сервиса (заявка = явный список, не файл в git)
делает такое поведение осмысленным иначе — либо явная кнопка "добавить транзитивные как
отдельные заявки", либо остаётся вне scope сознательно. Решить отдельно, не переносить как есть.

## SBOM (CycloneDX)

**Разрыв, требует подтверждения**: в конвейере self-service прототипа (`db_check → blacklist →
quarantine → license → download → vuln_scan → banner_scan → sast_scan → publish`,
`docs/architecture.md`) нет шага генерации SBOM. CI-версия генерирует CycloneDX SBOM по каждому
диффу (`sbom - create` job, использует внешние `get_license_v2.py`/
`generate_from_packagelist_license.py`). Если SBOM для одобренных пакетов нужен
потребителям (например, для соответствия/аудита) — это отсутствующий эпик, не мелочь.

## Political-banner / malicious-code — Sandbox отсутствует, приоритет №1 наравне с Docker

**Подтверждено по коду**: шаг `banner_scan` в прототипе — локальные YARA-правила
(`config/rules.yar`, тот же файл, что в CI, см. `docs/architecture.md`: "вердикт сервиса и CI не
расходится"). CI-версия **дополнительно** отправляет архив во внешний sandbox
(`$SANDBOX_URL/api/v1/scan/checkFile`) — динамический анализ (detonation), не только
сигнатурный. У прототипа такого шага нет вовсе.

**Статус — подтверждённый приоритет** (прямой запрос пользователя, `docs/flows.md`): Sandbox
явно назван как обязательная часть целевого флоу проверок, наравне с CVE/OSV, PoliticalBanner,
License, blacklist, SAST, карантином. Приоритет тот же, что у добавления Docker (см. выше) —
делать в первую очередь среди недостающей функциональности, не после остального.

**Важно при реализации**: конфигурация Sandbox (URL, API-токен) должна с самого начала быть
admin API + БД (шифруемый токен), а не временными env-переменными "на потом" — см.
`docs/configuration-model.md`, эта интеграция явно названа как пример того, что нужно
проектировать БД-конфигурируемым с первого коммита.

## SAST — временно выключено целиком (прямое решение пользователя, "на первых порах")

**Статус: выключено.** `sast_scan` в прототипе — `semgrep` внутри процесса
(`SAST_SCANNER_BIN`/`SAST_RULES`/`SAST_MIN_SEVERITY`, `SAST_ENABLED`). CI-версия триггерит
**отдельный GitLab-проект** (id 20443) через `crossbuilder run GitlabPipeline`. По прямому
решению пользователя обе реализации — и локальный semgrep в прототипе, и триггер внешнего
SAST-пайплайна — **выключены на первых порах**, не переносятся и не активируются, пока не
принято отдельное решение о возврате. Практически: `SAST_ENABLED=false` в конфигурации
Python-прототипа; в Go-версии шаг `sast_scan` и так ещё не реализован (`backend-go/internal/
pipeline`, шаги 0–3 сделаны) — при реализации фазы с шагами 4–8 этот шаг **не заводить**, пока
решение не изменится.

Не забыть, когда/если SAST вернётся в скоуп: у выделенного GitLab SAST-проекта (id 20443)
могли быть дополнительные правила/возможности сверх голого semgrep — сверить перед тем, как
считать локальный semgrep эквивалентом по умолчанию.

## Оповещения и упрувы — сверено отдельно и подробно

### Оповещения — канал только внутри сервиса, не туда, куда люди уже смотрят

**Подтверждено по коду**: единственная реализация — `InAppNotifier`
(`app/adapters/notifier.py`) — строки в таблице `notification`, видны только тем, кто зашёл в
UI/дёрнул `GET /api/v1/notifications`. Docstring прямо говорит: "Внешние интеграции (Mattermost,
Telegram) не реализуются". Список событий (`Event.*`) закрывает разумный набор
(`request_awaits_security`, `request_awaits_legal`, `license_claimed`, `comment_added`,
`decision_made`, `quarantine_released`, `package_revoked`, `package_approved`,
`pipeline_failed`) — но **все они уходят только в саму систему модерации**.

CI-версия толкала сигнал в инструменты, где разработчик/security-инженер и так смотрят:
GitLab MR notes (`prepare_mr_report`), `send_bot_message` политики, и — при вердикте
`DANGEROUS` от sandbox — отдельный **тикет YouTrack** (`/opt/task.py`), путь эскалации вовне
самого процесса модерации, с собственным SLA/трекингом.

**Разрыв реальный, не мелочь**: если пользователь не заходит в портал проактивно, событие
"ждёт вашего решения" он не увидит вообще — ни email, ни Slack/Mattermost, ни тикета. Для ролей
`legal`/`devsecops`, у которых это часть должностных обязанностей, это может быть приемлемо
(заходят регулярно), но для разработчика, который зашёл один раз и ждёт результата — нет
проактивного канала вообще. YouTrack как отдельная эскалация для action на `DANGEROUS`
вердикт — тоже отсутствует полностью.

### Упрувы — своя ролевая модель вместо нативного GitLab `approval_policy`, с одним подтверждённым разрывом

`moderation-security-policy-project` (CI-версия) — два `approval_policy`: лицензионная
(newly-detected/detected disallowed license → approve от группы 15171) и political
(critical SAST finding → approve от группы 11144), обе с
`prevent_approval_by_author`/`prevent_approval_by_commit_author`,
`prevent_pushing_and_force_pushing`, `fail: closed`.

Сверка по каждому свойству, не одной фразой:

- **`fail: closed` (недоступность проверки не пропускает автоматически)** — ✅ **сохранено**,
  подтверждено по коду: "недоступный сканер не значит чисто" применяется во всех content-scan
  шагах (`docs/architecture.md`).
- **Возобновление решения при новых данных** (аналог `remove_approvals_with_new_commit` —
  GitLab снимает старые approve при новом коммите) — ✅ **сохранено и сделано строже**:
  проверено отдельно, `rescan_approved()` (`app/tasks/scheduled.py`) перепроверяет уже
  `approved`-пакеты после каждого обновления снапшота OSV. `security_override_at` **не**
  используется как блокировка повторной проверки (в отличие от опасения, что технический долг
  из `architecture.md` про дублирование этой проверки в трёх шагах конвейера тут тоже сработает
  вхолостую) — rescan различает "тот же CVE, что уже был учтён при решении" (пакет остаётся
  approved) и "новый CVE выше порога" (**автоматически** `revoke_version` — снятие с публикации
  и отзыв артефакта, без участия человека). Подтверждено тестами
  `test_rescan_does_not_revoke_already_known_cve` и
  `test_rescan_revokes_on_genuinely_new_cve_after_override`. Это строже, чем в CI-версии, где
  такого автоматического пересмотра уже смерженного MR не было вовсе.
- **`prevent_approval_by_author`/`prevent_approval_by_commit_author` (нельзя одобрить своё же)**
  — 📋 **разрыв, подтверждён по коду**: ни `decide_security`, ни `decide_license`
  (`app/services/decisions.py`) не проверяют, что `actor.id != item.request.author_id`.
  Единственная проверка прав — роль (`require_roles` на уровне API). RBAC не запрещает одному
  пользователю одновременно иметь роли `developer` и `legal`/`devsecops` — если такое
  назначение ролей встречается на практике, пользователь технически может одобрить лицензию/
  безопасность для своей же заявки. В CI это было отдельным явным полем политики
  (`prevent_approval_by_author: true`), здесь — не проверяется нигде.
- **`prevent_pushing_and_force_pushing`/`block_branch_modification`** — не применимо к новой
  модели (нет больше веток/MR для пакетов), не разрыв.
- **Группа утверждающих — заранее заданный список людей (`group_approvers_ids`) vs роль**
  — **сознательное отличие модели**, не обязательно разрыв: в self-service любой пользователь с
  ролью `legal`/`devsecops` может решить за любую заявку, а не только специально назначенные
  15171/11144. Шире по составу решающих — если это нежелательно (например, роль `legal`
  выдаётся кому-то, кто не должен решать по конкретным продуктам), стоит явно решить, нужна ли
  более узкая, per-продуктовая авторизация.

## Retroactive purge заблокированных пакетов

**Требует проверки, не подтверждено**: CI-версия имеет отдельный режим `--delete` —
принудительно вычищает уже опубликованные в moderated-репозитории пакеты, попавшие в blacklist
задним числом. У прототипа есть `POST /api/v1/packages/{version_id}/revoke` (DevSecOps) — нужно
явно сверить, эквивалентен ли этот путь массовой чистке по blacklist-правилу, или revoke —
только точечное ручное действие по одной версии.

## Что в self-service прототипе строго лучше CI-версии (не разрыв, для баланса)

- Единая точка правды по правилам (blacklist/whitelist/лицензии — API+БД, не N копий файлов по
  проектам).
- Параллельные согласования юриста и DevSecOps (в CI лицензия блокировала весь пайплайн
  последовательно).
- Полный аудит-лог с историей решений (в CI — только логи CI с ограниченным сроком жизни).
- Кросс-заявочное распространение решений (`siblings_awaiting`) — в CI каждый MR/пайплайн был
  независим, одинаковый пакет в двух MR проверялся дважды с нуля.

## Как использовать этот документ при переносе на Go

Каждый раздел выше — кандидат в epic `user-stories.md`, но **не автоматически берётся в
scope** — прежде чем реализовывать что-то из списка, явно спросить/решить с пользователем,
нужно ли оно в целевой версии, а не переносить бездумно "потому что было в CI". Документ — чтобы
ничего не забылось, не чтобы всё автоматически реализовывалось.
