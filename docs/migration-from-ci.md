# Переход с `package_list.txt` и CI-проверок

Сервис — единственный вход для новых пакетов. Этот документ — план перехода команд, у которых
модерация раньше жила в `package_list.txt` и/или CI-джобах, которые ходили во внешние реестры
напрямую.

## Что меняется

| Было | Стало |
| --- | --- |
| Разработчик правит `package_list.txt` в MR | Разработчик создаёт заявку в сервисе (UI, `curl`, GitLab-ссылка) |
| CI сам ходит в pypi/npm/go/nuget за пакетом | CI ставит пакет из внутреннего репозитория (Nexus/Artifactory), пакет там появляется только после модерации |
| Проверки (если были) — скриптами в CI | Единый конвейер: blacklist → карантин → лицензия → скачивание → уязвимости → публикация |
| Список одобренного — файл в репозитории | База пакетов сервиса, поиск по имени/версии/менеджеру/статусу |

Merge request'ы для заведения пакетов больше не принимаются: правка `package_list.txt` не
запускает никакой процесс. Сервис ничего не пишет в репозитории и не открывает MR.

## Шаг 1. Одноразовый импорт существующих `package_list.txt`

Чтобы не заставлять команды перезаявлять уже одобренные пакеты, есть CLI-команда: она заносит
записи из существующего файла в базу сразу как одобренные, минуя конвейер, с указанием источника
в аудит-логе.

```bash
make import-list FILE=./services/billing/package_list_pypi.txt MANAGER=pypi
make import-list FILE=./services/billing/package_list_npm.txt MANAGER=npm
make import-list FILE=./services/billing/package_list_go.txt MANAGER=go
make import-list FILE=./services/billing/package_list_nuget.txt MANAGER=nuget
```

Эквивалент напрямую через `moderctl`:

```bash
moderctl import-package-list ./package_list.txt \
  --manager pypi \
  --actor admin \
  --origin "gitlab:group/billing:package_list.txt"
```

Формат файла — по одной записи на строку в формате менеджера (`name==version` для pypi и т. д.),
`#`-комментарии и пустые строки пропускаются. Строки, не подходящие под формат, считаются
`invalid` и в статистике команды показаны отдельно — их придётся завести вручную через обычную
заявку.

Команда идемпотентна: повторный запуск с теми же строками не создаёт дублей (уже одобренные
пропускаются как `skipped`).

**После импорта файлы в GitLab не читаются** — это одноразовая операция для внедрения, не
регулярная синхронизация. Если после импорта в `package_list.txt` добавили что-то ещё вручную (в
обход процесса) — это уже не будет подхвачено сервисом; такие пакеты нужно заявлять обычным
способом.

## Шаг 2. Разработчики переключаются на сервис

Раздайте команде ссылку на UI и, если используется SSO, — доступ через существующие группы
Keycloak/каталога (маппинг ролей уже настроен через `ROLE_MAPPING_*`, ничего дополнительно заводить
не нужно).

Для новых пакетов — четыре способа (UI → «Добавить пакеты»):

1. список пакетов;
2. файл зависимостей (`requirements.txt`, `package-lock.json`, `go.mod`, `packages.lock.json` и
   т. д.);
3. ссылка на файл в GitLab (после подключения GitLab в профиле);
4. быстрая проверка по базе без создания заявки.

## Шаг 3. CI переключается на внутренний репозиторий

Уберите из CI прямые обращения к pypi.org/registry.npmjs.org/proxy.golang.org/api.nuget.org (или
хотя бы сделайте внутренний репозиторий приоритетным источником) и укажите внутренний индекс.
Готовую команду для конкретного пакета сервис показывает в карточке пакета и в ответе API
(`install_command`); формат — тот же для любого пакета данного менеджера:

```bash
# pip
pip install -i https://nexus.internal.example.com/repository/pypi-internal/simple requests==2.31.0

# npm
npm i --registry=https://nexus.internal.example.com/repository/npm-internal/ lodash@4.17.21

# go
GOPROXY=https://nexus.internal.example.com/repository/go-internal GONOSUMCHECK=1 \
  go get github.com/gin-gonic/gin@v1.9.1

# nuget
dotnet nuget add source https://nexus.internal.example.com/repository/nuget-internal/index.json -n internal
dotnet add package Newtonsoft.Json -v 13.0.3 -s https://nexus.internal.example.com/repository/nuget-internal/index.json
```

Если пакета ещё нет во внутреннем репозитории — значит, по нему не было заявки или она не прошла
модерацию. Установка из CI в этом случае должна упасть — это ожидаемое поведение, а не баг
конфигурации.

## Шаг 4. Проверка по базе перед заведением заявки

Прежде чем заводить заявку на пакет, которым команда уже давно пользуется, стоит проверить базу —
может, он уже был заведён кем-то другим:

```bash
curl -sS -X POST http://localhost:8080/api/v1/packages/check \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"manager":"pypi","packages":["requests==2.31.0"]}'
```

Если пакет уже одобрен, `POST /api/v1/requests` тоже не создаст по нему новую заявку — вернёт
пометку `already_in_base` со ссылкой и командой установки.

## Что не переносится автоматически

- Транзитивные зависимости из старых `package_list.txt`, если они там были: сервис их не
  импортирует отдельно от прямых, если только они не заведены явными строками в файле. Если для
  сборки нужны конкретные транзитивные версии как отдельные разрешённые пакеты — заведите их
  обычной заявкой после импорта.
- История одобрений/причин из старого процесса (например, комментарии в закрытых MR) — в аудит-лог
  не переносится, там будет только запись `package_imported` с указанием источника и того, кто
  запустил импорт.
- Приватные CI-переменные с токенами старых реестров можно вывести из ротации после переключения
  на внутренний репозиторий — сервис их не использует.
