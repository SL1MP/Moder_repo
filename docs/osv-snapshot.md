# Снапшот базы OSV

Сканер шага 5 — **osv-scanner**, база — **локальный снапшот OSV из артефактори**. Сеть к osv.dev во
время проверки не используется: решение о каждой уязвимости принимается по данным, уже лежащим на
диске worker'а, и в БД фиксируется, по какой именно версии снапшота оно вынесено.

## Кто кладёт снапшот и куда

Снапшот загружает **существующий ежедневный скрипт заказчика** (вне этого сервиса) в артефактори:

```
{ARTIFACT_REPO_OSV}/{OSV_SNAPSHOT_PATH}
```

По умолчанию — `osv-snapshots/osv/latest/osv-all.zip`. Сервис ничего не публикует туда сам, только
читает.

## Формат файла

Один zip-архив (`.zip`), содержащий записи OSV в формате `.json` — по одной на файл, как их отдаёт
[OSV export](https://osv.dev/docs/#tag/api/operation/OSV_QueryAffected). Раскладка по директориям
внутри архива не важна: `OsvSnapshotIndex._records_for` ищет по трём кандидатам — `{Ecosystem}/`,
`{ecosystem}/` (нижний регистр) и корень архива, — так что подходят и плоская структура, и
разложенная по экосистемам (`PyPI/GHSA-....json`, `npm/GHSA-....json` и т. д.).

Пример записи (сокращённо):

```json
{
  "id": "GHSA-xxxx-yyyy-zzzz",
  "aliases": ["CVE-2024-1234"],
  "summary": "...",
  "severity": [{"type": "CVSS_V3", "score": "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H"}],
  "affected": [{
    "package": {"ecosystem": "PyPI", "name": "vulnpkg"},
    "ranges": [{"type": "ECOSYSTEM", "events": [{"introduced": "1.0.0"}, {"fixed": "1.4.3"}]}]
  }],
  "references": [{"type": "ADVISORY", "url": "https://..."}]
}
```

Значения `ecosystem`: `PyPI`, `npm`, `Go`, `NuGet` (см. `app/managers/versioning.py::OSV_ECOSYSTEMS`).
`GIT`-диапазоны игнорируются — они не применимы к версии из реестра.

## Определение версии снапшота

Версия, под которой снапшот попадает в таблицу `vuln_index_version`, не задаётся отдельным файлом
метаданных — она вычисляется из ответа артефактори на `HEAD`-запрос к файлу:

- если артефактори вернул `sha256`-хеш (заголовок `X-Checksum-Sha256`) — версия это первые 16
  символов хеша;
- иначе — время последней модификации файла (`Last-Modified`), в формате `20240520T040000Z`.

Так синхронизация остаётся идемпотентной даже без специального файла-манифеста: если файл не
менялся, версия не меняется, и `sync_osv_snapshot` не делает ничего (`no-op`).

## Синхронизация

Celery beat: задача `sync_osv_snapshot` по расписанию `OSV_SYNC_CRON` (по умолчанию `0 4 * * *`).

```
remote = HEAD ARTIFACT_REPO_OSV/OSV_SNAPSHOT_PATH
if remote.version == локально загруженная версия:
    no-op
else:
    payload = GET ARTIFACT_REPO_OSV/OSV_SNAPSHOT_PATH
    проверить sha256(payload) против заявленного (если артефактори отдал именно sha256)
    распаковать во временную директорию OSV_LOCAL_DB_PATH.new
    атомарно подменить OSV_LOCAL_DB_PATH
    записать/обновить строку в vuln_index_version, пометить is_active
    поставить задачу rescan_approved
```

Ручной запуск:

```bash
make sync-osv                       # без принуждения — только если появился новее
make cli ARGS="sync-osv --force"    # перезагрузить тот же снапшот
```

или из UI: «Настройка» → карточка «База уязвимостей OSV» → «синхронизировать снапшот» (роль
`devsecops`/`admin`).

## Поведение при недоступности или устаревании

Если снапшот недоступен (артефактори не отвечает, файла нет по пути) или его возраст превышает
`OSV_MAX_STALENESS_DAYS` (по умолчанию 3 дня):

- **автоматическое одобрение отключается**: шаг 5 конвейера возвращает `warn`, а не `pass`,
  даже если найденных уязвимостей нет;
- причина фиксируется явно: «база уязвимостей устарела»;
- пакет уходит в очередь DevSecOps (`awaiting_security`) — решение принимается вручную;
- **молча одобрять на устаревших данных нельзя** — это осознанное ограничение, а не баг.

Если снапшот не загружался вообще (`current_version() is None`), поведение то же: `is_stale`
возвращает `True`.

Пока сам файл читается (`OsvSnapshotIndex.sync`) и **не найден** в артефактори — это ошибка
`upstream_error`, шаг 5 завершится `fail` с понятным сообщением; в норме к этому моменту снапшот
уже когда-то был успешно загружен, и `query()` продолжает работать по последней рабочей копии,
пока не появится новая.

## Перепроверка после обновления

После **успешной** загрузки нового снапшота (`sync_osv_snapshot` вернул `synced: true`)
автоматически ставится задача `rescan_approved`:

- проходит по всем `package_version.status == 'approved'`;
- запрашивает `VulnerabilityIndex.query()` по новому снапшоту;
- если максимальный балл превысил `VULN_MAX_SCORE` — пакет переводится в `revoked`, снимается с
  публикации в артефактори (`ArtifactStore.delete`), DevSecOps и авторам заявок с этим пакетом
  уходит уведомление `package_revoked`;
- перед отзывом сервис обращается к уже опубликованной копии в артефактори
  (`ArtifactStore.download`) — не заново к внешнему реестру, — чтобы зафиксировать, что решение
  принято по тому же артефакту, что был выдан пользователям.

Ручной запуск: `make rescan` или `moderctl rescan`.

## Режим только для разработки

`OSV_SOURCE=api` переключает `VulnerabilityIndex` на `OsvApiIndex` — прямые запросы к
`api.osv.dev` (`OSV_API_URL`). У этого источника `is_stale()` всегда возвращает `False` (свежесть
не имеет смысла для live-API). **Не используется в бою**: продовый профиль полагается на
`OSV_SOURCE=snapshot`, чтобы не ходить наружу во время проверки и не зависеть от доступности
publicого сервиса.
