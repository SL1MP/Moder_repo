## Коротко

Сервис самостоятельной модерации пакетов: разработчик заводит заявку, конвейер
проверяет пакет, роли согласуют спорное, одобренное публикуется во внутренний
репозиторий.

**Перенос backend'а с Python на Go завершён.** Каждый маршрут python-версии имеет
пару в Go, nginx проксирует в `api-go` весь префикс `/api/`, контейнеры `api`,
`worker`, `beat` и `redis` выведены из стека по умолчанию под профиль `python` —
они остаются только как способ отката.

| | |
|---|---|
| На Go | всё: заявки, конвейер, решения, очередь, обсуждения, уведомления, отчёты, вход, транзитивные зависимости, регламентные задачи, админка и «Настройка», GitLab, CLI |
| На Python | ничего из повседневной работы; код цел и поднимается профилем `python` |
| Go-код | ~31 600 строк без тестов, 135 файлов, 479 тестов |
| Миграции | 15 (golang-migrate) + 10 (alembic), парные |
| Пакетные менеджеры | 12: pypi, npm, go, nuget, maven, docker, conan, luarocks, terraform, php, git, files |

## Что изменилось в этот заход

Шесть изменений, заказанных отдельно от переноса.

### Конвейер: минус два шага, плюс один

Сняты `banner_scan` (политические баннеры, YARA) и `sast_scan` (semgrep). Реализация
обоих сохранена — `internal/scanners`, `pipeline.RetiredSteps`, — и коды шагов
остаются допустимыми значениями в базе: строки `pipeline_step` с ними лежат у каждой
заявки, проверенной до снятия, и такая заявка обязана читаться. Возврат в строй —
добавление шага обратно в `Steps`/`StepCodes` плюс миграция.

Добавлен `sandbox_scan`: архив уходит в песочницу, оттуда приходят вердикт и отчёт.

| Вердикт | Что делает сервис |
|---|---|
| `CLEAN` | `pass`, конвейер идёт дальше |
| `DANGEROUS` | `fail`, публикация заблокирована, решение за DevSecOps |
| `UNWANTED` | `pass` **с пометкой в отчёте** |
| песочница недоступна | `warn` → `awaiting_security`: «проверить нечем» — не то же самое, что «чисто» |

`UNWANTED` пропускается по решению заказчика: это «нежелательное, но не вредоносное» —
рекламные модули, майнеры в примерах, агрессивная телеметрия. Блокировать по нему
значило бы звать DevSecOps на каждый второй пакет.

Конвейер теперь: `db_check → blacklist → quarantine → license → download → vuln_scan →
sandbox_scan → publish`.

### Отказ от S3

MinIO убран. Скачанный пакет всё время лежит в артефактори, но в двух разных
репозиториях: временном (`ARTIFACT_REPO_STAGING`) — пока идут проверки, и репозитории
своего менеджера — после того, как все пройдены. Отчёты переехали в третий
репозиторий (`ARTIFACT_REPO_REPORTS`).

Перенос между репозиториями делается **силами самого артефактори** (`api/move`), без
прогона байтов через сервис; где это не поддерживается — сервис перекладывает
скачиванием и выгрузкой. Разница видна в поле `publish_mode` отчёта.

Зачем: отдельное объектное хранилище — это ещё одна система со своими ключами,
сетевым доступом и резервным копированием, ради файлов, которые и так едут только в
артефактори.

### Двенадцать пакетных менеджеров вместо четырёх

Добавлены maven, docker, conan, luarocks, terraform, php, git, files.

Три из них устроены иначе остальных и потому стоят отдельного слова:

* **`files`** — модерация готового архива или двоичного файла. Реестра нет, версию и
  имя задаёт человек, проверка идёт по содержимому.
* **`git`** — модерация репозитория. Скачивается срез по ссылке и ревизии, дальше
  обычный конвейер.
* **`docker`** — образ забирается по Docker Registry v2 API со всеми платформами
  манифеста и складывается в OCI image layout. Все платформы, а не только текущая:
  уязвимость в `linux/arm64` не перестаёт существовать оттого, что собирали на amd64.

### База OSV: три источника на выбор

Заказан был выбор вариантов — сделаны все три, переключаются `OSV_DB_SOURCE`.

| | `artifactory` (по умолчанию) | `http` | `file` |
|---|---|---|---|
| Где лежит | raw-репозиторий артефактори | любой адрес | диск воркера |
| Доступ | уже настроен, тот же токен | нужен отдельный | не нужен |
| Откуда версия | `X-Checksum-Sha256` / `Last-Modified` | `ETag` / `Last-Modified` | время изменения и размер |

Разбор компромиссов — `docs/osv-snapshot.md`. Способ ни на что, кроме способа
доставки, не влияет: файл раскладывается на диск целиком, версия фиксируется в базе,
проверка идёт по локальным данным.

### Закрыты служебные долги

`golang-migrate` в compose отдельным сервисом `migrate-go`; перезагрузка политик без
рестарта; ограничение частоты запросов; бизнес-метрики Prometheus (имена 1:1 с
python-версией); повторы и circuit breaker на вызовах к реестрам.

### Дошёл остаток переноса

Три маршрута (`/packages/check`, `/packages/{id}/revoke`, `/items/{id}/license-claim`),
админка и «Настройка», GitLab (включая формат шифрования токенов — уже сохранённые
подключения продолжают работать), и CLI: `bootstrap`, `import-packages`,
`service-account`.

## Что сделано (общая картина)

### Конвейер и заявки

Восемь шагов, очередь на Postgres (`FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY`), сторож
зависших пакетов, повторы упавших прогонов, возобновление с нужного шага после решения
роли.

Заявки: создание тремя способами (перечисление, файл зависимостей, файл из GitLab),
разбор `requirements*.txt`, `poetry.lock`, `pyproject.toml`, `package-lock.json`,
`yarn.lock`, `package.json`, `go.mod`, `go.sum`, `packages.lock.json`,
`packages.config`, `*.csproj`; идемпотентность по `Idempotency-Key`; закрытие заявки
автором.

### Решения ролей

Карантин, вердикт DevSecOps, вердикт юриста, заявление лицензии. Главное в этой части —
**распространение на siblings**: решение выносится по версии пакета, а не по заявке, и
доходит до всех, кто эту версию заказал. Без этого одинаковый пакет в чужой заявке
висел бы заблокированным навсегда.

### Транзитивные зависимости

Раскрытие дерева по данным реестров, приведение каждого требования к точной версии по
правилам своей экосистемы (semver, PEP 440, интервалы NuGet, MVS у Go).
`POST /api/v1/dependencies/resolve` показывает дерево **до** создания заявки. Обрезка по
пределу, нераскрытые зависимости и конфликты версий называются вслух — это про то,
чего в дереве нет.

### Регламентные задачи

Внутри `worker-go`, расписание то же, что было у celery beat:

| Задача | Как часто | Что было без неё |
|---|---|---|
| снятие истёкшего карантина | 15 мин | пакет стоял «в карантине до даты» вечно |
| уборка временного репозитория | 2 часа | временная зона росла, пока есть место |
| загрузка снапшота OSV | 6 часов | «база устарела», каждый пакет к DevSecOps вручную |
| перепроверка одобренных | после новой базы | уязвимость, найденная после одобрения, оставалась незамеченной |

Разово — `moderation maintenance [--quarantine|--cleanup|--osv-sync|--rescan]`.

### Командная строка

`serve`, `worker`, `migrate`, `schema`, `maintenance`, `scan`, `bootstrap`,
`import-packages`, `service-account`.

`bootstrap` репозитории артефактори **проверяет, а не создаёт** — в отличие от
python-версии. Создание там умел только Nexus своим админским REST API, для JFrog
Artifactory эквивалента нет вовсе, а токен сервиса в промышленном контуре прав на
заведение репозиториев не имеет и иметь не должен. Полезен же не факт создания, а ответ
на вопрос «доедет ли сервис туда, куда будет класть пакеты».

### Вход, интерфейс, стенд

OIDC/Keycloak (Authorization Code + PKCE), локальный вход для сервисных учёток, роли из
групп каталога, RBAC на маршрутах. Русскоязычный SPA. `docker compose` со всем стеком,
профили `sso`, `nexus` и `python`, `moderation schema` — сверка схемы базы с кодом.

## Проблемы и что с ними стало

Всё перечисленное всплыло на живом стенде или на проверке. В скобках — коммит.

| Что видел пользователь | В чём было дело | Итог |
|---|---|---|
| «Найдено уязвимостей: 0», а в отчёте 4 находки | счётчик заполнялся до проверки того, отработал ли сканер вообще | считаем только по отработавшему прогону, «сканер не отработал» — отдельное состояние (`addda58`) |
| SAST вообще не запускался | `semgrep-core` падал от **пустой** переменной `HTTP_PROXY`, которую подставлял compose | пустые прокси-переменные вычищаются перед запуском сканера (`44c49f1`) |
| «Заявка не закрыта», «Решение не применено» | в базе не было миграции 0008 — сервис писал в несуществующие столбцы | ошибки схемы называют себя и говорят, какую миграцию накатить; появилась команда `moderation schema`; `migrate-go` в compose (`eb7eb31`, `70655d4`, `7351ff9`) |
| Отчёт не открывался: «Не передан Bearer-токен» | отчёт открывался обычной ссылкой, а браузер не шлёт заголовок авторизации по `<a href>` | отчёт запрашивается с токеном и показывается в изолированном `iframe` (`7b13d1d`) |
| Пакет «в очереди», но никто его не берёт | воркер мог не подобрать пакет, и это ничем не лечилось | сторож очереди внутри `api-go` забирает залежавшиеся пакеты и громко пишет о каждом (`6d99f43`) |
| `pull access denied for minio/minio` | образ MinIO больше не отдаётся с Docker Hub анонимно | вопрос снят вместе с MinIO: хранилища больше нет (`0fac445`) |
| «Не удалось получить конфигурацию OIDC-издателя» | сообщение не отличало «Keycloak не поднят» от «realm назван иначе» | сообщение называет адрес, код ответа и следующий шаг (`77f2c68`) |
| «Артефактори отклонил публикацию (405)» на каждом пакете | в go-версию попала только реализация для Artifactory, а стенд на Nexus: на `PUT` он отвечает 405 | перенесена вторая реализация, тип выбирается `ARTIFACT_STORE` и проверяется на старте (`f6e241a`) |
| Заявка по `poetry.lock` приезжала пустой | формат не различает прямые и транзитивные записи, все считались транзитивными и отбрасывались фильтром | такие файлы принимаются целиком с предупреждением (`0780855`) |
| Очереди ролей отвечали 500 | **своя регрессия**: в SQL-запрос добавили столбцы, в разбор строки — нет | поймано тестами очередей до стенда (`e2c9898`) |
| `docker compose up` не поднимался вовсе: «service "minio" has neither an image nor a build context» | при отказе от S3 сервис убрали из базового файла, но не из оверлеев, а `docker-compose.override.yml` подхватывается автоматически | оверлеи S3 удалены целиком, блоки `minio` убраны из `override` и `prod` (`e96bd91`) |

Отдельно — две вещи, которые выглядели как поломка, но поломкой не были: пакет в
карантине до даты (штатно, лечится регламентной задачей) и «база уязвимостей устарела»
(снапшот ни разу не загружали; теперь воркер забирает его сам).

## Долги и риски

Перечислено то, что известно и пока не сделано. Замалчивать такое дороже, чем признать.

1. **Стенд открыт наружу с паролями по умолчанию.** Postgres и Keycloak слушают
   `0.0.0.0`, пароли — из `.env.example`. Для локальной машины терпимо, дальше нет.
2. **Песочница не проверена на настоящем сервисе.** Клиент написан по присланному
   шаблону задачи GitLab CI, разбор ответа защищён от изменений формата
   (`data.result.verdict`, полный ответ сохраняется в отчёт), но живого вызова не было.
   Первое, что стоит сделать на стенде.
3. **Публикация в Artifactory через `api/move` не проверена на бою.** Что перенос
   не поддерживается, сервис узнаёт по ответу и откатывается на «скачать и выгрузить»,
   но какой из путей окажется рабочим у заказчика — неизвестно. `ARTIFACT_DRY_RUN=true`
   существует ровно для этой проверки.
4. **Публикация в Nexus работает только для pypi, npm, nuget и go.** Для восьми новых
   менеджеров реализован Artifactory; на Nexus они упрутся в «не задан формат
   компонента». Это осознанное ограничение, а не недосмотр: компонентный API Nexus
   требует своей раскладки на каждый формат.
5. **Нет SBOM (CycloneDX)** — в CI-версии он генерируется по каждому диффу.
6. **Конфликты версий транзитивных зависимостей не разрешаются** — обе версии попадают
   в заявку и помечаются конфликтом. Выбирать за разработчика сервис не вправе.
7. **Маркеры окружения** (`python_version < "3.8"`) не вычисляются: раскрывается
   лишнее. Промодерировать лишний пакет дешевле, чем пропустить нужный.
8. **Python не удалён, а погашен.** Пока идёт обкатка, каталог `backend/`,
   alembic-набор и профиль `python` остаются. Когда откат перестанет быть нужен,
   удаляется всё разом.

## План

1. **Обкатать на стенде** то, что нельзя проверить без него: песочницу, `api/move` в
   артефактори, перенос пакета между репозиториями, восемь новых менеджеров на живых
   реестрах.
2. **Удалить Python**, когда обкатка пройдёт: каталог `backend/`, профиль `python`,
   `redis`, alembic-набор. До тех пор откат — один флаг.
3. **Закрыть стенд**: сеть, пароли, секреты — перед выходом за пределы локальной машины.
4. **Развитие**: SBOM по каждой заявке, ретроспективная чистка заблокированных пакетов,
   публикация новых менеджеров в Nexus (если у заказчика он, а не Artifactory).

## Как проверяем

Три приёма, которые уже несколько раз оправдались:

* **Мутационное тестирование.** После каждого набора тестов вносится поломка в код и
  проверяется, что тесты падают. Тест, который не падает на сломанном коде, не проверяет
  ничего. Так были найдены повторное снятие карантина, молчащий кэш снапшота и — в этот
  заход — неверное имя столбца в заполнении справочника лицензий и потеря пароля
  демо-учёток при повторном `bootstrap`.
* **Живой стенд.** Postgres, настоящие реестры, интерфейс в настоящем браузере.
  Утверждения вида «работает» делаются только после такого прогона; всё, что проверить
  не удалось, помечено как непроверенное (см. «Долги и риски», пп. 2–4).
* **Дифференциальная проверка против эталона.** Там, где реализуются чужие правила,
  свои тесты проверяют понимание правил, а не сами правила. Схемы версий прогнаны против
  `packaging` и `semver`: 73 200 пар «требование/версия» по pypi и 2 185 500 по npm,
  расхождений нет. Формат шифрования токенов GitLab сверен с настоящей библиотекой
  `cryptography` в обе стороны — иначе уже сохранённые подключения перестали бы
  открываться.

Прогон тестов с базой — **только `go test -p 1 ./...`**: база одна на все пакеты, часть
тестов проверяет состояние сервиса целиком, и параллельный прогон ломает не код, а тест.
База между прогонами не пересоздаётся, поэтому тест, заводящий строку с
общеизвестным именем, обязан убирать её за собой.
