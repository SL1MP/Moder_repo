# Выгрузка SBOM в VuMana

Конвейер формирует CycloneDX из тех же байтов, которые были скачаны и будут
опубликованы. После завершения параллельных проверок документ обогащается
результатами OSV и определённой лицензией, затем отдельный шаг
`sbom_upload` отправляет его в VuMana.

Корневой `metadata.component.group` всегда равен
`com.ptsecurity.moderated`. Для Maven исходная группа GAV в самом компоненте
пакета при этом сохраняется; для Docker не добавляется фиктивный `vendor` в
PURL. `metadata.tools` отражает фактически использованный генератор, а не
подменяет его название и версию из примера другого CI-конвейера.

Контракт повторяет `sbom-utils/scripts/vumana/upload_sbom.py`:

- `POST {VUMANA_API_URL}/sbom/upload`;
- `multipart/form-data`;
- поле `file` содержит CycloneDX JSON;
- успешный ответ — HTTP 200 и JSON с полем `url`.

Настройки доступны в web-разделе **VuMana**:

| Переменная | Назначение |
|---|---|
| `VUMANA_ENABLED` | включает выгрузку |
| `VUMANA_API_URL` | служебный API, например `https://vumana.example/api` |
| `VUMANA_URL` | адрес интерфейса для ссылки на отчёт |
| `VUMANA_TOKEN` | необязательный Bearer-токен |
| `VUMANA_TIMEOUT_SECONDS` | таймаут одного документа |

Недоступность VuMana фиксируется результатом `info` и не блокирует публикацию:
это соответствует прежнему CI job, где `upload_sbom.py` выполнялся с
`|| true`. Сам SBOM остаётся доступен в карточке заявки и хранилище отчётов.

Порядок выполнения:

1. blacklist и карантин;
2. скачивание артефакта;
3. параллельно: лицензия, OSV, песочница, Dragon и формирование SBOM;
4. обогащение и выгрузка SBOM в VuMana;
5. публикация во внутренний артефактори после проверки блокировок.
