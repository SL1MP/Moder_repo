# Модель конфигурации — от `.env`+рестарт к admin API + БД

Решение (прямой запрос пользователя): **все параметры, которые использует сервис, должны быть
настраиваемы через пользовательский ввод** — URL и токены Artifactory, URL и токен sandbox,
политики блокировки (blacklist/лицензии/пороги) и так далее. Это меняет текущий принцип
прототипа ("экран «Настройка» — только чтение, правка `.env` + рестарт", `README.md`) на
принцип, уже принятый в `sentrix` (SSO там настраивается во время выполнения через `/admin/sso`,
хранится в Postgres, а не статично в `.env`) — единство с референсами, тот же throughline, что
и весь остальной этот документооборот.

## Принцип (уточнён, второй заход)

Уточнение пользователя: **редактируемым и удобным должен быть ввод любой переменной**, не
только той, что технически можно хранить в БД. Это снимает кажущееся противоречие с прошлой
версией документа ("bootstrap-исключение остаётся в `.env`") — противоречия на самом деле нет:
неверно было бы говорить "эти переменные не редактируются", правильно — **они редактируются
другим механизмом**, потому что не могут храниться в БД, к которой сами же обеспечивают
доступ (DSN Postgres — классический пример: не может быть записью в базе, до которой ещё не
достучались). Три уровня, не два:

| Уровень | Где живёт | Как редактируется | Когда применяется |
| --- | --- | --- | --- |
| **1 — горячий** | БД, admin API | форма в «Настройке», сразу | без рестарта |
| **2 — тёплый** | БД, admin API (тот же UI) | та же форма, с пометкой "требует перезапуска" | после `restart`, значение уже сохранено и провалидировано заранее, не вручную в файле |
| **3 — bootstrap** | `.env`/секрет-хранилище | **guided setup-мастер** (`moderctl init`/аналог), не сырой текстовый файл — валидация полей, подсказки, генерация секретов | до первого старта или через отдельную процедуру ротации |

Уровень 3 — не "неудобно" и не "недоделано", это единственный технически корректный способ
хранить то, без чего сервис не может прочитать конфигурацию из БД (иначе — бесконечная
рекурсия: DSN базы лежит в базе). "Удобный пользовательский ввод" для уровня 3 достигается не
переносом в БД, а тем, что мастер настройки заменяет собой ручную правку `.env` (валидация на
месте, подсказки по каждому полю, безопасная генерация секретов, а не "придумайте случайную
строку сами") — см. раздел "Удобство пользовательского ввода" ниже.

## Полная сверка — что куда, по каждой переменной `.env.example`

### Уровень 3 — bootstrap, редактируется мастером настройки, не сырым `.env`

| Переменная | Почему не может жить в БД |
| --- | --- |
| `POSTGRES_HOST/PORT/DB/USER/PASSWORD`, `DATABASE_URL` | это подключение к самой БД — где хранился бы её же конфиг |
| `REDIS_URL`/`CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` (в целевой Go-версии — брокер задач, см. отдельное решение по Sentrix/Vumana-модели) | подключение к брокеру нужно раньше, чем сервис может прочитать что-либо из БД |
| `FERNET_KEY` | ключ шифрования — сам шифрует записи в БД, не может быть записью в БД, которую шифрует |
| Учётные данные bootstrap-администратора | первый вход, пока больше ничего не настроено — см. открытый вопрос №4, решение ниже |
| `APP_ENV`, `LOG_LEVEL` | режим самого процесса — технически мог бы быть Уровнем 2 (тёплым), но настолько редко меняется в проде, что не стоит усложнять; пересмотреть, если понадобится менять `LOG_LEVEL` на лету при инциденте (частый реальный сценарий — тогда это скорее Уровень 2) |
| `PUBLIC_BASE_URL`, `NGINX_*`, `*_PORT`, `*_IMAGE`, `KEYCLOAK_ADMIN`/`KEYCLOAK_ADMIN_PASSWORD` | деплоймент/инфраструктура (docker-compose, обвязка контейнеров), меняется вместе с топологией развёртывания, не через сам сервис |
| `LOCAL_AUTH_SECRET` | **устраняется полностью**, не переносится ни в БД, ни остаётся в `.env` — заменяется PAT + server-side сессиями без статического секрета, см. `docs/auth.md` |

Для этого уровня "удобный ввод" = `moderctl init` (или аналог) — интерактивный мастер при
первом развёртывании: спрашивает каждое значение по очереди, валидирует на месте (проверка
досягаемости Postgres/брокера прямо во время ввода, не постфактум при падении контейнера),
сам генерирует секреты (`FERNET_KEY`, пароль bootstrap-администратора) вместо "придумайте
случайную строку сами", пишет итоговый `.env` — человек не редактирует текстовый файл руками
с нуля, только подтверждает/донастраивает то, что мастер уже подготовил.

## Хранение и защита секретов

- Шифруемые поля (`ARTIFACT_TOKEN`, sandbox-токен, `OIDC_CLIENT_SECRET`, `GITLAB_OAUTH_CLIENT_SECRET`)
  — тем же механизмом, что уже используется для `user.gitlab_*_token_enc` (Fernet, ключ — из
  `.env`, единственное настоящее bootstrap-исключение среди секретов). Не изобретать второй
  механизм шифрования для второго набора секретов.
- В API/UI такие поля никогда не возвращаются в открытом виде повторно (как уже сделано для
  GitLab-токенов — "Токены GitLab никогда не возвращаются в API", `docs/api.md`) — только
  маска/факт наличия, замена — только полной перезаписью.
- Каждое изменение — запись в `audit_log` (кто, что, старое→новое — для секретов "старое
  значение" в логе должно быть тоже маской, не расшифровкой).

## Удобство пользовательского ввода — конкретные требования к UI, не только "сделать форму"

По уточнению пользователя ("пользовательский ввод должен быть удобен") — набор конкретных, а
не абстрактных требований к экрану «Настройка» (и к мастеру уровня 3):

- **Типизированные поля, не голый текст**: булевы значения — переключатель, перечисления
  (`ARTIFACT_STORE=nexus|generic`, `ARTIFACT_AUTH_TYPE=basic|token`) — выпадающий список, а не
  текстовое поле, где можно опечататься мимо допустимых значений; числа — с единицами измерения
  рядом (`SAST_TIMEOUT_SECONDS` → подпись "секунд", не просто число без контекста) и
  min/max-валидацией на месте.
- **Секреты — маска + замена целиком**, не "покажите старое значение, чтобы я его
  подправил" (уже зафиксировано в разделе "Хранение и защита секретов" — здесь именно с точки
  зрения удобства: поле явно показывает "задано / не задано", кнопка "заменить", не попытка
  показать частично или подсказать длину, которая ничего не даёт пользователю).
- **Валидация на месте, до сохранения** — не "сохранили — потом узнали на живом трафике, что
  URL с опечаткой". Минимум — формат (URL, число в допустимом диапазоне); там где дёшево —
  живая проверка (см. следующий пункт).
- **Кнопка "проверить подключение" на каждой интеграции** (уже отмечено как идея в
  `docs/ux-wishlist.md`, здесь — как конкретное требование к самой форме ввода, не отдельная
  функция где-то ещё): рядом с полями Artifactory/Sandbox/OSV/GitLab/OIDC — кнопка, которая
  прямо из формы редактирования делает тестовый вызов (HEAD/health-подобный, не боевую
  операцию) и показывает "работает"/"ошибка: <текст>" до нажатия "Сохранить".
- **Явная пометка "требует перезапуска"** там, где это Уровень 2 — не молчаливое "сохранили, а
  почему не применилось — непонятно" (см. таблицу выше, столбец "Уровень").
- **Предпросмотр изменения перед сохранением** (diff "было → станет"), особенно для групповых
  настроек вроде правил blacklist — уже отмечено в `docs/ux-wishlist.md`, здесь подтверждается
  как требование, не просто идея на вырост.
- **Поиск/фильтр по названию переменной** внутри экрана «Настройка» — при ~90 параметрах
  (текущий `.env.example`) плоский список без поиска неудобен уже сейчас, будет хуже с ростом
  числа интеграций (Docker, Sandbox, остальные пакетные менеджеры).
- **Контекстная подсказка на каждое поле** — `SETTINGS_CATALOG` уже хранит `description` для
  каждой переменной (`app/core/config.py`) — переиспользовать её как подсказку прямо у поля
  ввода, не только в режиме чтения, как сейчас.
- **Импорт/экспорт целиком** (JSON/YAML) — для переноса конфигурации между окружениями
  (staging → prod) без ручного повторного ввода всех ~90 значений по одному; секреты при
  экспорте — не выгружаются в открытом виде (пустые поля/плейсхолдер, требующие отдельного
  ввода на целевом окружении).

## Что не меняется

- `GET /settings` остаётся как способ увидеть **действующие значения**, в т.ч. Уровня 3 (для
  диагностики важно видеть всё в одном месте, даже то, что редактируется не через этот экран).
- Экран «Настройка» (`SettingsPage.tsx`) перестаёт быть **только** read-only: секции Уровня 1/2
  получают форму редактирования (доступно роли `admin`, отдельные секции — `devsecops`/`legal`
  по аналогии с уже имеющимся разделением прав на `osv-sync`). Секции Уровня 3
  (инфраструктурные/bootstrap) остаются read-only **на этом экране** — их редактирование живёт
  в отдельном мастере/CLI (см. Уровень 3 выше), не потому что им не полагается удобный ввод, а
  потому что редактирующий их UI не может зависеть от уже запущенного приложения.

## Открытые вопросы

1. **Правила YARA/semgrep — содержимое файла в БД или путь к файлу, который БД только
   указывает?** Правила — не короткие строки типа URL, это полноценные файлы правил
   (`config/rules.yar`, semgrep-конфиги). Хранить как BLOB/TEXT в БД (полностью
   БД-конфигурируемо, но менее удобно редактировать большие правила через веб-форму) или
   оставить путь к файлу настраиваемым, а само содержимое — вне БД (частичное исключение из
   принципа "всё конфигурируемо")? Нужно явное решение, не бездумно "и это тоже в БД".
2. **HTTP-клиенты (`internal/httpclient`/`app/core/http.py`) должны уметь горячо
   перечитывать таймауты/circuit breaker без рестарта процесса** — сейчас конфиг читается один
   раз при старте (`get_settings()` с кэшированием). Переезд в БД без изменения этого — значит,
   поле в UI обновится, а реальный HTTP-клиент — нет, до рестарта. Нужен явный механизм
   инвалидации (аналог `admin/reload`, но для всех переехавших групп, не только blacklist/
   licenses).
3. **`HTTP_PROXY`/`NO_PROXY` в БД** — если прокси меняется, но клиент уже создан с прежним
   транспортом (см. `docs/integrations.md`, "клиенты реестров используют эти значения явно"),
   нужен тот же механизм горячей инвалидации; отдельно — стоит ли вообще делать прокси
   БД-настраиваемым, если это скорее свойство сети/деплоя, чем бизнес-политика — решить явно,
   не молча исключить.
4. **Bootstrap-администратор — решение предложено, не окончательно подтверждено пользователем.**
   Факт по коду не изменился: `app/services/seeds.py`, `DEMO_USERS` — демо-сид, не боевой
   механизм; в проде роль `admin` сегодня появляется только через уже настроенный OIDC или
   ручной `moderctl` с доступом к машине. С переездом OIDC на Уровень 2 (БД) возникает
   проблема курицы и яйца, которой сейчас нет — предложенное решение: **мастер уровня 3
   (`moderctl init`) сам заводит bootstrap-администратора** как часть первичной настройки —
   генерирует логин/пароль (или принимает от оператора), сохраняет как Уровень 3 (не в БД, тем
   же способом, что `FERNET_KEY`), выводит один раз при установке. Это закрывает и "удобный
   ввод" (не вручную выдумывать пароль), и саму проблему курицы и яйца (вход всегда есть, даже
   если OIDC ещё не настроен или сломан) — ровно паттерн sentrix
   (`ADMIN_BOOTSTRAP_USERNAME/PASSWORD`), только выдаваемый мастером, а не вручную в `.env`.
5. **Порядок миграции**: делать это в текущем Python-прототипе (быстрее увидеть результат,
   но переписывать почти сразу на Go) или сразу проектировать как часть Go-версии
   (`docs/migration-to-go.md`) — не тратить работу на реализацию, которая тут же заменяется?
   Учитывая масштаб (новые таблицы, admin API на запись, формы UI для десятка групп настроек)
   — вероятно, разумнее сразу в Go, но это стоит решить явно, не по умолчанию.
