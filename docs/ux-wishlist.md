# Что можно сделать для удобства каждой роли — черновой брейншторм

**Статус: неотфильтрованный брейншторм**, не согласованный бэклог. Задача — набросать максимум
идей по каждой роли (`docs/stakeholders.md`), не отобрать "правильные" — приоритизация и отсев
отдельным шагом, с пользователем. Где идея закрывает уже найденный конкретный разрыв — явная
ссылка на источник; где идея новая, придуманная сейчас, — без ссылки.

## Разработчик

- 📎 Уже известно (`docs/flows.md`): автообновление карточки заявки останавливается ровно
  тогда, когда начинается ожидание решения человека — почему бы не возобновлять поллинг (или
  переключаться на server-sent events/WebSocket) при переходе в `awaiting_*`, не только в
  `pending`.
- 📎 Уже известно: нет внешнего канала уведомлений (email/Mattermost/Telegram) —
  `docs/ci-parity-gaps.md`.
- Браузерные push-уведомления (Notification API) — не требует внешней интеграции, работает
  прямо из открытой вкладки.
- Подписка на конкретный пакет ("сообщите мне, если появится новая уязвимость/отзыв уже после
  того, как я поставил его") — не только на свою заявку.
- CLI для разработчика (не только `moderctl` для админов) — `pip install`-подобный опыт:
  `modctl add pypi requests==2.31.0`, чтобы не открывать браузер ради разовой проверки.
- Drag-and-drop файла зависимостей вместо выбора через диалог; автоопределение менеджера по
  содержимому файла (уже есть `managers/detect?filename=` по имени — расширить до анализа
  содержимого, не только расширения).
- Групповые операции: выбрать несколько пакетов из результатов "не найдено" и одной кнопкой
  завести на каждый отдельную заявку с разным обоснованием, а не только одним общим текстом.
- Подсказка "похожий пакет уже одобрен" при вводе имени (fuzzy-поиск по базе) — на случай
  опечатки в имени/версии до отправки.
- Оценка "обычно такие заявки рассматриваются N часов" на основе исторических данных — снижает
  тревожность ожидания.
- История заявок с фильтром "мои отклонённые" — учиться на своих ошибках, не спрашивать заново
  у DevSecOps то же самое.
- Тёмная/светлая тема (SPA уже тёмная по умолчанию — добавить переключатель, не считать чужим
  решением).
- Экспорт списка одобренных пакетов проекта в SBOM-подобный файл — самостоятельно, без запроса
  к DevSecOps.
- Комбинированный "инспектор пакета" — на одной странице сразу CVE, лицензия, история версий,
  альтернативы, а не только карточка текущей заявки.

## CI / автоматизация

- 📎 Уже известно: PAT со scope вместо токена уровня учётки (`docs/auth.md`).
- 📎 Уже известно: нельзя отозвать токен одного пайплайна отдельно (`docs/user-stories.md`).
- Официальные клиентские библиотеки/SDK (Python, Go) поверх REST API — не заставлять каждую
  команду писать свой `curl`/`jq`.
- Готовые шаблоны для GitLab CI/GitHub Actions ("вставьте этот job") — по аналогии с тем, как
  `moderated/*.yml` были готовыми шаблонами для CI-версии, только теперь — тонкий вызов сервиса.
- Машиночитаемый вывод в стандартных форматах (SARIF для находок, CycloneDX для одобренных
  зависимостей) — чтобы результат сразу понимали существующие дашборды/интеграции без парсинга
  специфичного JSON.
- Кэш результата `packages/check` на стороне клиента с ETag/If-None-Match — при частых
  перезапусках одного пайплайна не долбить API одними и теми же пакетами.
- Явный `GET /api/v1/health/ci` — облегчённый healthcheck специально для CI (без деталей
  worker'а), чтобы пайплайн мог быстро проверить доступность сервиса до основного вызова.
- Пакетная проверка по нескольким файлам зависимостей за один вызов (монорепа с несколькими
  `requirements.txt`) — сейчас один вызов — один файл.

## Security-инженер / DevSecOps

- 📎 Уже известно: нет проверки на самоодобрение (`docs/ci-parity-gaps.md`).
- Сохранённые фильтры/представления очереди ("мои", "просрочено >3 дней", "по продукту X").
- Массовое решение по классу находок — например, "разрешить всё с CVSS < 90 из этой партии"
  одним действием вместо по одному, с явным подтверждением и записью в аудит на каждый
  затронутый пакет отдельно (не терять трассируемость ради скорости).
- Кнопка "занести в blacklist" прямо с карточки находки — не отдельный поход в конфигурацию.
- Витрина трендов: доля отклонённых/одобренных по времени, топ причин отказа, самые
  "проблемные" пакеты/экосистемы — для отчётности и приоритизации правил.
- SLA-таймер на карточке — сколько заявка ждёт решения, эскалация (см. ниже, уведомления) при
  превышении порога.
- Сравнение "чем эта версия отличается от предыдущей одобренной" (diff зависимостей/лицензии/
  находок) — вместо разбора с нуля каждый раз.
- Групповая (per-продукт/per-команда) настройка порога уязвимостей и списка approved-лицензий —
  не один глобальный порог на всех потребителей.
- Интеграция с существующей внутренней базой знаний CVE/инцидентов — ссылка "уже разбирали
  такое" на карточке уязвимости.
- Уведомление за N часов до истечения SLA, не только по факту нарушения.

## Юрист / Legal

- 📎 Уже известно: нет проверки на самоодобрение.
- Библиотека шаблонных ответов ("MIT — стандартно разрешена", "GPL — требует отдельного
  согласования с руководителем продукта") — не печатать одно и то же вручную.
- Матрица совместимости лицензий (какие лицензии конфликтуют друг с другом в одном продукте) —
  сейчас юрист держит это в голове.
- Делегирование/бэкап-утверждающий на время отпуска — без выдачи роли `legal` временному
  человеку вручную через `moderctl`.
- Массовое решение по одинаковому SPDX среди нескольких *разных* пакетов (не той же версии —
  это уже покрыто sibling-propagation, а именно "MIT встречается в 5 разных ожидающих заявках
  сегодня").
- Экспорт решений по лицензиям за период — для внешнего аудита/комплаенс-отчётности одним
  файлом, не через `audit_log` вручную.

## Администратор

- 📎 Уже известно: единственный способ читать аудит — роль `admin` целиком (`docs/auth.md`).
- 📎 Уже известно: незавалидированный дефолт `LOCAL_AUTH_SECRET` (`docs/architecture.md`).
- Предпросмотр изменений конфигурации до применения ("что изменится, если сохранить") — особенно
  важно, когда конфигурация переедет в admin API (`docs/configuration-model.md`) и станет
  редактируемой через форму, не только просматриваемой.
- История версий конфигурации с возможностью отката ("кто и когда поменял порог CVSS, откатить
  на предыдущее значение") — `audit_log` уже фиксирует факт, не хватает удобного отката одним
  кликом.
- Импорт/экспорт blacklist и справочника лицензий как CSV/YAML — массовое редактирование вне UI
  для больших списков, с последующей загрузкой обратно.
- Баннер "плановые работы" — предупредить пользователей о даунтайме заранее, не только постфактум
  в уведомлениях.
- Управление ролями пользователей через UI, не только `moderctl` из командной строки.
- Дашборд здоровья интеграций одним взглядом (Artifactory/Sandbox/OSV/GitLab/Keycloak — живы ли,
  когда последний успешный вызов) — сейчас `GET /system/status` знает только про worker/очередь.

## Аудитор / комплаенс-ревьюер

- 📎 Уже известно: нет отдельной read-only роли (`docs/auth.md`) — простейшее и самое ценное
  улучшение для этой роли, всё остальное вторично, пока это не сделано.
- Готовые отчёты "для аудита" (кто/что/когда за период, по шаблону, который обычно просят
  внешние аудиторы) — не сырой `audit_log`, а агрегированный вид.
- Неизменяемый экспорт (подписанный/с хешем) — чтобы отчёт можно было предоставить внешней
  стороне как доказательство, а не просто скриншот таблицы.

## SRE / оператор сервиса

- Единая точка входа "что не так прямо сейчас" — уже есть `queue-doctor`, расширить его же
  логику на остальные интеграции (Artifactory/Sandbox/OSV недоступны — не только про очередь).
- Готовые алерты Prometheus (не просто метрики — сразу правила alerting, соответствующие
  подходу `deploy/prometheus/alerts.yml` у sentrix) — сейчас метрики есть, готовых правил нет.
- Runbook-ссылки прямо в алерте (по аналогии с тем, что уже задокументировано в README
  "queue-doctor") — не искать документацию отдельно во время инцидента.
- Синтетический health-check "полный путь" (заводит тестовый пакет через весь конвейер по
  расписанию, кроме реальной публикации — с `ARTIFACT_DRY_RUN`) — раннее обнаружение деградации
  до жалоб пользователей.

## Владельцы интеграций (Artifactory/Keycloak/GitLab/OSV/прокси)

- Self-service проверка "правильно ли я всё настроил" — тестовая кнопка в admin UI ("проверить
  подключение") на каждую интеграцию сразу после ввода креды, не дожидаясь первого реального
  прогона конвейера, который может упасть спустя долгое время (ровно то, что произошло с EULA
  Nexus в моей локальной проверке — эта кнопка поймала бы это за секунды, не за час отладки).
- Понятная диагностика при первом запуске — если Artifactory/Sandbox/Keycloak недоступны при
  старте, явный чеклист в логе/UI, что проверить, а не голый таймаут.

## Мигрирующая команда (переход с `package_list.txt`)

- Дашборд прогресса миграции — сколько команд уже перешли, сколько пакетов осталось
  неимпортированными, а не только команда `import-package-list`, запускаемая вручную по одной.
- Автоматическое обнаружение устаревших прямых обращений к публичным реестрам в CI-конфигах
  команды (эвристика по `.gitlab-ci.yml`) — подсказать, что переключение на внутренний реестр
  ещё не завершено, не дожидаться, пока кто-то заметит вручную.

## Сквозные идеи (не привязаны к одной роли)

- Полнотекстовый поиск по всему (заявки, комментарии, аудит, пакеты) — сейчас поиск разрознен
  по разным экранам с разными фильтрами.
- Горячие клавиши для частых действий в очередях (разрешить/отклонить без мыши) — DevSecOps/
  legal разбирают десятки карточек в очереди, экономия секунд на карточку заметна на масштабе.
- Локализация UI на английский (сейчас только русский) — если в организации есть
  англоязычные сотрудники/подрядчики.
- Мобильная адаптация — хотя бы для чтения статуса/уведомлений и простых решений
  (разрешить/отклонить) с телефона, не для полноценной работы.
- API-версионирование с самого начала (`/api/v1` уже есть — убедиться, что breaking changes
  не ломают уже написанные CI-интеграции потребителей без предупреждения).

## Явно не проверено, требует решения перед тем как брать в работу

Всё выше — идеи, не оценённые по трудозатратам и не согласованные с существующими решениями
(например, "полнотекстовый поиск" и "локализация" — заметно больше работы, чем "кнопка
проверить подключение"). Следующий шаг — не реализация списком, а совместная приоритизация:
что реально нужно в первую очередь, а что можно вычеркнуть как красиво звучащее, но не
востребованное.
