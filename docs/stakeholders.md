# Стейкхолдеры

Роли и интеграции — по фактическому коду сервиса (`backend/app`), не по предположениям: сервис —
самостоятельный self-service портал (см. `README.md`, "Сервис — единственный вход"), не
CI-обвязка и не GitLab-webhook receiver. Правки `package_list.txt` и merge request'ы как способ
завести пакет не поддерживаются; переход с этой модели описан в
[`migration-from-ci.md`](migration-from-ci.md). Целевой технический стек — Go, см.
[`migration-to-go.md`](migration-to-go.md); стейкхолдеры от языка реализации не зависят.

Для каждой роли: **кто**, **точки взаимодействия** (конкретные экраны UI / эндпоинты API),
**цели**, **как сейчас** (✅ уже работает в прототипе / 📋 разрыв, см. `user-stories.md`),
**по чему можно измерить, что роли хорошо**.

## Разработчик (роль `developer`)

**Кто:** любой сотрудник, которому нужен внешний пакет в проекте. Роль по умолчанию для новых
пользователей, заходящих через SSO без специального маппинга группы.

**Точки взаимодействия:** UI «Добавить пакеты» (список / файл зависимостей / ссылка на GitLab /
быстрая проверка), `POST /api/v1/requests`, `POST /api/v1/packages/check`,
`GET /api/v1/requests/{id}`, обсуждение под заявкой (`comments.py`).

**Цели:** минимальное время от "нужен пакет" до "есть команда установки"; когда пакет не готов
сразу — понятная причина (`blocked_reason`) и явное "что делать" (`next_action`), а не голый
статус.

**Как сейчас:** ✅ все четыре способа заведения заявки реализованы; ✅ заявку может создать
любая роль, не только `developer`; ✅ авто-мерж для уже одобренной версии (`already_in_base`) без
повторной заявки.

**Разрыв:** 📋 нет способа узнать заранее (до заявки), что версия уже была отклонена/в
blacklist — `packages/check` возвращает найденное состояние, но UI явно не подсказывает
альтернативную (не заблокированную) версию.

**Важная особенность модели:** решение по пакету, который уже используется в другой заявке (той
же версии), может прилететь не от собственного действия заявителя — см. `architecture.md`,
абзац про `siblings_awaiting`/`_apply_to_siblings`.

**Метрика:** медианное время от создания заявки до `approved`/финального статуса, разбитое по
тому, на каком шаге чаще всего стоит (квартиль ожидания).

## CI / автоматизация (машинный актор, не человек)

**Кто:** пайплайны, заводящие заявки без интерактивного пользователя — `curl` с
`Authorization: Bearer`, `Idempotency-Key`, часто в блокирующем режиме (ждут финального статуса
синхронно перед тем, как продолжить сборку — см. `docs/api.md`).

**Точки взаимодействия:** те же `POST /api/v1/requests`/`packages/check`, что и у разработчика,
но программно, не через UI.

**Цели:** предсказуемая идемпотентность (повтор с тем же `Idempotency-Key` не плодит заявки),
токен для CI не должен требовать интерактивного OIDC-логина, права токена должны быть уже
ощутимо *уже*, чем права полноценного пользователя (CI не должно уметь ничего, кроме "завести
заявку/проверить статус").

**Как сейчас:** ✅ идемпотентность на `moderation_request.idempotency_key`; 📋 **разрыв** —
единственный неинтерактивный способ получить токен сейчас (`LOCAL_AUTH_ENABLED`) выдаёт
сервисной учётке ровно те же права, что были бы у неё в UI (роль целиком, не отдельное
разрешение "только создавать заявки"); нет отзываемого токена с ограниченной областью действия
(аналог PAT). См. `docs/auth.md`, раздел про CI-токены.

**Метрика:** доля сборок, упавших из-за таймаута ожидания решения (а не из-за реального отказа
пакета) — показывает, разумно ли пайплайны используют блокирующий режим.

## Security-инженер / DevSecOps (роль `devsecops`)

**Кто:** разбирает очередь безопасности, владеет порогами уязвимостей и правилами сканирования
содержимого.

**Точки взаимодействия:** `GET /api/v1/queue/security`, `decide-security`,
`release-quarantine`, `POST /api/v1/packages/{version_id}/revoke`, `config/rules.yar`,
`VULN_MAX_SCORE`/`SAST_MIN_SEVERITY`/`SAST_RULES`.

**Цели:** видеть уязвимости/баннеры/SAST-находки в одном месте с файлом и строкой; одним
решением снимать все три блокировки разом; не терять пакет молча, если сканер недоступен.

**Как сейчас:** ✅ реализовано полностью, включая централизованный `security_override_*` (с
оговоркой — проверка продублирована в трёх местах кода, см. `architecture.md`, план на
исправление при переносе на Go).

**Метрика:** доля пакетов, застрявших в `awaiting_security` дольше N дней (SLA очереди); число
случаев `moderation_watchdog_recovered_total` — коррелирует с нагрузкой на инфраструктуру
сканирования, не с этой ролью напрямую, но полезно для приоритизации.

## Юрист / Legal (роль `legal`)

**Кто:** рассматривает заявленные лицензии, ведёт справочник допустимых SPDX.

**Точки взаимодействия:** `GET /api/v1/queue/legal`, `decide-license`, `license_claim`
(url/snapshot/SPDX), `config/licenses.yml`.

**Цели:** решение по лицензии не должно ждать своей очереди после других шагов и не должно
блокировать DevSecOps — согласования идут параллельно.

**Как сейчас:** ✅ реализовано полностью, включая параллельность с шагом безопасности.

**Метрика:** доля заявленных лицензий, для которых `license_claim` содержит достаточно данных
для решения с первого раза (без дополнительных вопросов в обсуждении заявки).

## Администратор сервиса (роль `admin`)

**Кто:** конфигурирует сервис, разбирает инциденты очереди, управляет сервисными учётками.

**Точки взаимодействия:** `GET /api/v1/admin/audit`, `POST /api/v1/admin/reload`,
`GET /api/v1/system/status`, `POST /api/v1/admin/queue-sweep`, `osv-sync`,
`moderctl create-service-account`.

**Цели:** правки правил/справочников без деплоя (`reload`), видимость состояния очереди без
пяти разных команд (`queue-doctor`), полный аудит "кто/что/когда/откуда".

**Как сейчас:** ✅ реализовано; ⚠️ явный операционный риск — `LOCAL_AUTH_SECRET` не
провалидирован при старте (см. `architecture.md`), устраняется вместе с переходом на PAT-модель
CI-токенов (`docs/auth.md`).

**Разрыв:** 📋 экран «Настройка» — только чтение (осознанное решение, не баг), но нет
UI-подтверждения "правки применены" после `reload` кроме кода ответа API — стоит решить, нужен ли
тут UX-фидбэк заметнее.

**Метрика:** время от инцидента (worker лёг) до восстановления — измеримо через
`queue-doctor`/`moderation_watchdog_recovered_total`.

## Аудитор / комплаенс-ревьюер (отдельная от `admin` точка зрения)

**Кто:** периодически проверяет, что процесс модерации соблюдается (внутренний аудит
безопасности, комплаенс, иногда — внешний аудитор при сертификации). Не обязательно имеет роль
`admin` — по факту сейчас доступ к аудиту завязан на неё, см. разрыв ниже.

**Точки взаимодействия:** `audit_log` (кто/что/когда/старое-новое/источник), история
`pipeline_step` по любому пакету.

**Цели:** ответить на вопрос "почему именно эта версия пакета одобрена" без обращения к
разработчикам сервиса — вся история должна быть в БД, не в логах с ограниченным сроком жизни.

**Как сейчас:** ✅ `audit_log` фиксирует достаточно данных (см. `architecture.md`, "Сущности").

**Разрыв:** 📋 нет отдельной read-only роли для аудита — сейчас `GET /api/v1/admin/audit`
доступен только `admin` (значит, тот, кто выдаёт права полного администратора аудитору,
превышает необходимое). У oakshield (`DSO-track`) есть отдельный `access_audit`-эндпоинт и
собственная вкладка «Журнал доступа», не требующая роли администратора целиком — стоит
рассмотреть похожее разделение, см. `docs/auth.md`.

## Команда разработки сервиса (мейнтейнеры)

**Кто:** те, кто пишет и поддерживает код сервиса — не пользователи процесса модерации, а его
авторы.

**Точки взаимодействия:** `docs/development-standards.md`, `docs/architecture.md`,
`docs/migration-to-go.md`, тесты (`backend/tests/`), CI-гейты.

**Цели:** предсказуемые конвенции (валидация на границе, sentinel-ошибки, тестирование на
реальном Postgres — уже сформулировано), не терять инженерные решения (watchdog, atomic claim,
circuit breaker) при переносе на Go.

**Как сейчас:** ✅ конвенции задокументированы для Python-версии; 📋 при переносе на Go —
принять эквивалентные, ориентируясь на `sentrix` (см. `docs/testing.md`, план ниже).

## Владелец инфраструктуры реестра (Nexus/Artifactory)

**Кто:** эксплуатирует целевой hosted-репозиторий (`ArtifactStore`: Nexus по умолчанию либо
внешний JFrog-совместимый Artifactory).

**Цели:** сервис публикует только через абстракцию, идемпотентно; репозитории создаются
автоматически при bootstrap.

**Как сейчас:** ✅ реализовано, вторая реализация (`generic`) уже есть как референс для будущих
адаптеров (SeaweedFS при переносе на Go — см. `migration-to-go.md`).

## Downstream CI / потребители внутреннего репозитория

**Кто:** пайплайны команд, ранее ходившие напрямую в pypi.org/registry.npmjs.org/
proxy.golang.org/api.nuget.org, теперь ставящие пакеты только из внутреннего реестра.

**Цели:** предсказуемая команда установки (`install_command`); отсутствие пакета в реестре —
ожидаемый сигнал "не было заявки/не прошла модерацию", а не баг конфигурации.

**Как сейчас:** ✅ реализовано, см. `migration-from-ci.md`, шаг 3.

## Владелец каталога/IdP (Keycloak или совместимый OIDC)

**Кто:** администрирует realm/группы для маппинга ролей (`ROLE_MAPPING_*`).

**Цели:** сервис не хранит пароли обычных пользователей; предсказуемое поведение при
разворачивании под реальным доменом (HTTPS обязателен из-за PKCE/`window.crypto.subtle`).

**Как сейчас:** ✅ реализовано, включая приём обоих issuer'ов (внутренний/публичный).

## Владелец GitLab-интеграции (только чтение)

**Кто:** администрирует OAuth-приложение в GitLab (scope `read_api`/`read_repository`) для
одного способа завести пакет — чтения файла зависимостей из приватного проекта.

**Как сейчас:** ✅ реализовано; секрет `FERNET_KEY` шифрует refresh-токены пользователей.

## Владелец снапшота базы уязвимостей (OSV)

**Кто:** обеспечивает регулярную публикацию снапшота OSV в артефактори, который сервис читает
по расписанию — без обращения к `api.osv.dev` в боевом режиме.

**Цели:** свежесть снапшота напрямую влияет на решения (`OSV_MAX_STALENESS_DAYS`).

**Как сейчас:** ✅ реализовано.

## Владелец корпоративного прокси

**Кто:** обслуживает `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` для всего исходящего трафика к
реестрам и GitLab.

**Как сейчас:** ✅ реализовано, клиенты используют значения явно, не полагаются на окружение
процесса.

## SRE / оператор сервиса

**Кто:** следит за здоровьем очереди и worker'а (heartbeat, метрики по шагам конвейера,
circuit breaker, возраст снапшота OSV, число зависших пакетов).

**Инструмент диагностики:** `make queue-doctor` — единый отчёт, отличающий "worker не запущен"
от "worker жив, но слушает не те очереди".

**Как сейчас:** ✅ реализовано для стека Celery/Redis; при переносе на Go меняется реализация
(NATS/Valkey), не набор гарантий — см. `migration-to-go.md`.

## Команда, переходящая с `package_list.txt`/CI (переходная роль)

**Кто:** тимлиды/security-контакты команд, чьи проекты раньше подключали `moderated`
CI-шаблоны — одноразовый импорт (`moderctl import-package-list`) и переключение CI на
внутренний индекс.

**Как сейчас:** ✅ реализовано, см. `migration-from-ci.md`.

**Что теряется при переходе (осознанно):** история одобрений из старых MR, транзитивные
зависимости, явно не заведённые строками в файле.

## Соотношение с ранее описанной архитектурой на Go/webhook (`../moderation-service/`)

В той же рабочей папке ранее был начат альтернативный дизайн (Go + Postgres + webhook-driven,
без self-service UI, MR-центричная модель). Дальнейшая работа идёт от `moderation-repo/`. Стек
теперь тоже сходится (backend этого прототипа переезжает на Go, см. `migration-to-go.md`) —
расходится только модель работы. `../moderation-service/docs/*` по-прежнему стоит явно разобрать
(см. открытый вопрос №2 в `docs/migration-to-go.md`).
